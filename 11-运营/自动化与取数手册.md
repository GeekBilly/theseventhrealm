## 附：本机 shell 陷阱（在 macOS 上跑本项目脚本前必读）

macOS 自带的是 BSD 工具，不是 GNU coreutils —— **下面每一条都实际踩过**。

| 坑 | 现象 | 正确做法 |
|---|---|---|
| `sed -i ''` | BSD sed 不接受空后缀 | 用 **`sed -i.bak`**（会留 `.bak`，记得清） |
| `grep` BRE 不支持 `\|` | 交替匹配静默失效 | 用 **`grep -E`**，或直接用 Grep 工具 |
| **无 GNU `timeout`** | `timeout: command not found`，且**整条命令被静默跳过**（最危险：看起来像"执行了但没输出"） | **后台启动 ＋ 轮询**，或改用 `python3` 自己控超时 |
| ⚠️ **`nohup … &` 跑长脚本，输出会整段丢失** | 日志文件被创建但**始终 0 字节**，脚本其实已跑完 —— 与「真失败」无法区分 | ⭐ 用**工具自带的后台参数**启动（输出会被回收，可再取回）；**别用 shell 的 `&`**（`path-links-check.py` 实测踩到，连跑两次为空） |
| `head -n -N` | 不支持负数 | 用 `python3` 或 `tail` 组合 |
| 系统 Chrome 无头截图 | 被沙箱拦，拿不到图 | 用真机截图，或改用 Playwright 等独立浏览器 |
| **`grep` 对个别 UTF-8 文件整体失灵** | **无输出 ＋ 退出码 1，但内容确实存在** | 改用 **Read 工具**或 `python3 -c "print(repr(...))"`；**绝不据此判断「改动没落盘」** |
| Bash 工具误判命令 | 命令里含 `sc`/`reg` 等字样时被当成系统级工具而拒绝 | 把脚本写进 `/tmp/*.py` 再执行 |

> ⚠️ 判断「文件到底改没改」的**唯一可靠方法**：`python3 -c "print(repr(open(p,encoding='utf-8').read()[:200]))"`，
> **不要看 grep 有没有命中，也不要看退出码**。

## 积分自动取数（fetch-credits.sh）排障 runbook —— 2026-10-05 实测

### 三层通道优先级
1. **9222 CDP**（最快）：`curl http://127.0.0.1:9222/json/version` 通 → `fetch-credits-cdp.sh` → `fetch-credits-cdp.mjs`
2. agent-browser + 持久 profile（`/Users/billyhou/.workbuddy/browser-profile`）
3. 都失败 → 降级：用账本最后一条真实余额，在仪表盘顶部标注数据时点

### 坑 1：Chrome 起不来（GPU process isn't usable. Goodbye.）
启动**必须**带：`--no-sandbox --disable-setuid-sandbox --disable-gpu --disable-crash-reporter`
（本机其它存活实例都带这三个，照抄即可）

### 坑 2：Chrome 被连带杀掉
`nohup ... &` + `disown` 不够——工具调用结束时整个进程组被回收。
必须用 python `subprocess.Popen(args, start_new_session=True)` 新建 session 脱离。
`open -na "Google Chrome" --args ...` **实测不生效**（起不来）。

### 坑 3：agent-browser 取不到数（Failed to fetch）
`agent-browser connect` 后会**绑死在一个自己新建的 about:blank 目标**上；
而 workbuddy.cn 的**登录态按标签页存（sessionStorage）**，新标签没有登录态 → 同源 fetch 必失败。
解法：绕开 agent-browser，自己 `GET /json/list` 挑中 `workbuddy.cn/profile/plans-usage` 那个标签，
拿它的 `webSocketDebuggerUrl` 直连 CDP，`Runtime.evaluate {awaitPromise:true, returnByValue:true}`。
已封装为 `11-运营/scripts/fetch-credits-cdp.mjs`（node 22 自带全局 WebSocket，无需装 ws 包）。

### 坑 4：osascript 操作 Chrome 会挂死
本机多实例时 `tell application "Google Chrome" to activate` 会 hang，工具调用被 SIGTERM（exit 137）。
别用。要置顶让用户自己点（`--user-data-dir` 独立 + `-n` 会在 Dock 多出一个 Chrome 图标）。

### 为什么前三条路都不通（实测结论，别再试）

| 方案 | 症状 | 根因 |
|---|---|---|
| **v1** agent-browser | `eval` 恒报 `Failed to fetch`；`Unexpected token '<'` | daemon 的 active tab 永远是 `about:blank`，JS 打在空白页上；登录失效后拿到登录页 HTML 当 JSON —— **晨检连错 9 天的真凶** |
| **v2** 无头 Chrome 复用持久 profile | 必被 302 到 `/login/` | 登录走 Keycloak，`AUTH_SESSION_ID` 是 **session cookie，进程一关就失效**；只有 `session` 这个 httpOnly cookie 是 7 天持久的，但新进程读不到有效值 |
| **v3** 导出 cookie / 抓 Authorization 头 → curl 直调 API | 网关（APISIX）返回 401 | 抓包显示 headers 里**根本没有 Authorization**，真实凭据是浏览器自动附加的 httpOnly cookie，**进程外拿不到** |
| **v4 常驻无头 Chrome + CDP（当前）** | ✅ 稳定取数 | 登录态只能活在浏览器进程里 —— 那就让它一直活着 |

### 架构

```
start-credits-browser.sh   ← 只在首次 / 电脑重启后跑（弹二维码，扫一次）
   └─ 后台常驻无头 Chrome，9222 端口，标签停在 /profile/plans-usage

fetch-credits.sh           ← 日常取数，全自动、零人工、零浏览器窗口
   └─ 探测 9222 → 标签不在积分页就先导航 → CDP 直连取数 → 落盘 JSON
```

### 两条命令

| 场景 | 命令 | 人工 |
|---|---|---|
| 首次 / **电脑重启后** | `11-运营/scripts/start-credits-browser.sh` | ✅ 扫一次码 |
| **日常取数** | `11-运营/scripts/fetch-credits.sh [port] [out.json]` | ❌ 全自动 |

- `fetch-credits.sh` 第二参数可指定落盘路径，默认 `/tmp/credits-real.json`；成功才写，失败不覆盖旧值。
- 落盘后可直接喂仪表盘：`python3 11-运营/scripts/build-dashboard.py /tmp/credits-real.json -o 11-运营/reports/积分仪表盘-<日期>.html`

### 输出字段

单行 JSON：`ok / fetchedAt / window / remain / cycleUsed / cycleTotal / pkgCount / isPaidUser / rowsInWindow / byDay[] / sum7 / avg7`

### 退出码

| 码 | 含义 |
|---|---|
| 0 | 成功（stdout 单行 JSON，同时落盘） |
| 1 | `NEED_LOGIN` —— 常驻 Chrome 没在跑或登录态过期，跑 `start-credits-browser.sh` 重扫 |
| 4 | 环境缺失（无 Chrome / 无 node） |
| 5 | 页面未就绪 / 取数失败 |

### 关键坑（重写时踩的，别再踩）

1. **必须用 `--user-data-dir` 指定独立 profile**：不指定会转发给已运行的 Chrome，新实例立刻退出 → 调试端口不起。
2. **`--no-sandbox --disable-gpu --disable-dev-shm-usage` 必加**：本环境下 Chrome 内部沙箱起不来（`sandbox initialization failed: Operation not permitted`）。
3. **禁止把 Chrome 输出接 `| head`**：管道满 15 行后 SIGPIPE 会把 Chrome 杀掉（本次因此白跑两轮）。要重定向到文件再读。
4. **同一个 profile 不能有两个 Chrome**：启动前先 `pkill -f "remote-debugging-port=9222"`。
5. **登录页要先勾选协议再点「同意」**，否则二维码 iframe 不加载（第一张截图是空的就是这个原因）。
6. **`security add-generic-password` 不能用 `printf | ` 从 stdin 喂密码**，会被静默忽略；必须显式 `-w "<值>"`，写完立刻回读验证。
7. **登录态有服务端有效期**（`session` cookie 约 7 天，到 2026-10-16）+ **电脑重启即失效**（session cookie 性质，绕不过）。到期表现＝`fetch-credits.sh` 输出 `{"error":"NEED_LOGIN"}`，重跑 `start-credits-browser.sh` 扫一次即可恢复。

## 刷新服务（工作台 / 晨检看板上的「刷新数据」按钮）

页面是生成好的静态 HTML，**自己不会取数**。想点一下就看到新数据，靠的是本地这个服务。

| 项 | 值 |
|---|---|
| 脚本 | `11-运营/scripts/refresh-server.py` |
| 端口 | `127.0.0.1:8787`（被占则顺延到 8788…） |
| 页面入口 | `http://127.0.0.1:8787/`（工作台）· `/board`（晨检看板）|
| 日志 | `11-运营/data/refresh-server.log` |

### 端点

| 端点 | 作用 |
|---|---|
| `GET /ping` | 存活探测。页面先探它，探不到就退化成「重新载入」 |
| `GET /status` | 当前指标（只读本地台账，不取数） |
| `POST /refresh` | 真刷新：**五步**＝站点体检 → 积分真取数 → 站点流量采集 → 重建看板片段 → 重建工作台（约 30–60 秒） |
| `POST /refresh?upload=1` | 同上 + 覆盖更新资料库两个节点（= 同步云端） |
| `GET /once` | 与 `/refresh` 等价，方便 curl / launchd |

### 前端行为（写死在 `qj_refresh.py`，两个页面共用）

- 服务在：POST `/refresh` → 状态灯**原地重绘**（不重载也能看到新数）→ 0.9 秒后整页重载拿完整新内容。
- 连不上时**按场景给不同提示**（别再合并成一句，会误导）：
  - 云端页 → 「云端页连不到本机服务（浏览器规则）…」
  - 本机页 → 「刷新服务未启动…在终端跑 refresh-server.py」
  两种都退化为 `location.reload()`。资料库在线页点它＝拉最近一次同步上来的版本。
- **Shift + 点**＝刷新并同步云端（默认不同步，改线上内容必须显式动作）。
- 刷新结果写 `sessionStorage`，重载后仍按最新一次显示，不会闪回旧值。

### 启动

```bash

python3 11-运营/scripts/refresh-server.py

# 常驻 —— 🔴 必须在「你自己的终端」跑这两行：
#   我在沙箱里没有装载权限：launchctl bootstrap/load 一律返回
#   "Bootstrap failed: 5: Input/output error"，crontab 也是 operation not permitted。
cp 11-运营/scripts/com.theseventhrealm.refresh.plist ~/Library/LaunchAgents/

# 装完自检：launchctl list | grep theseventhrealm　→　应看到 com.theseventhrealm.refresh
# ⚠️ 但这个自检**只能在你自己的终端跑**：我在沙箱里永远 grep 不到（看不到你的 GUI 域），
#    会误判成「没装」。我的判断办法是看进程命令行——plist 起的是**绝对路径**
#    （/Users/.../refresh-server.py），我自己临时起的是相对路径（11-运营/scripts/...）。

# 只跑一次（不启服务）
python3 11-运营/scripts/refresh-server.py --once

# 定时自动刷新（不点按钮也自己跑，最小间隔 30 分钟）
python3 11-运营/scripts/refresh-server.py --every 30                # 只改本地
python3 11-运营/scripts/refresh-server.py --every 30 --auto-upload   # 刷完同步云端
```

> **为什么要有 `--every`**：云端页（https）连不到本机 `127.0.0.1`，在那儿点刷新只能是重新载入。
> 想让云端也能看到新数，只能把取数搬到服务端定时跑：本机跑完（可选同步云端）后，
> 云端点刷新重载即可拿到最近一次结果，**滞后不超过一个周期**。
> `--auto-upload` 等于定时改线上内容，脚本层**默认不开**，要开得自己加这个参数。
> **2026-10-09 已确认开启**：本机实例与 plist 均带 `--every 30 --auto-upload`。

> 🔴 **2026-10-11 实测：launchd 起的服务上传认证失败**
> `{"error":"获取上传凭证失败: code=E_AUTH_FAILED; msg=PAR failed"}`
> —— 上传接口拿不到凭据（本机 WorkBuddy 会话里手动跑 `--upload` 是正常的）。
> ⇒ **`--auto-upload` 定时同步云端目前实际不生效**：定时刷新照常更新**本地**数据，
> 但云端只在手动同步时更新。日志里出现 `build-morning-board.py FAIL` 且原因为
> `E_AUTH_FAILED` 时，＝“本地刷新成功、云端未同步”，不是刷新坏了。

### 坑

1. **必须带浏览器 UA**：探针里已写死，否则 Cloudflare 返回 403（不是站点故障）。
2. **资料库在线页连不上 `127.0.0.1`**（https 页面请求 http 会被浏览器拦掉）——这是浏览器规则，不是脚本坏了。要看活数据，在本机打开 `http://127.0.0.1:8787/`。
3. **同一时刻只跑一次刷新**：重复点击返回 `busy`，不会并发跑两遍（脚本重建同一批文件，并发会互相覆盖）。
4. 体检只覆盖本次取到的字段，取不到的**保留上次值**而不是清空——避免一次网络抖动就把看板刷成「本次未提供」。
