# 站点性能诊断与优化方案 · 2026-10-17

> 结论先行：**站点自身没有 performance issue，慢的是跨境链路。**
> 唯一属于站点、且真能改的杠杆是「HTML 没进 CDN 缓存」—— 见第三节，需你批准后才能动。

## 一、测了什么

新增脚本 `11-运营/scripts/perf-check.py`，对每页分别测：

| 项 | 测法 | 含义 |
|---|---|---|
| 冷（回源） | URL 加 `?__cb=<时间戳>`，强制 CDN 未命中 | 真实用户第一次打开 |
| 热（CDN） | 预热后连测 | 命中缓存能有多快 |
| gap ＝ 冷 − 热 | 两者相减 | **属站点自己的开销**（把链路噪声减掉） |
| size | `--compressed` 后体积 | 模拟真实浏览器收到的字节 |
| cache | `cf-cache-status` | HIT / DYNAMIC |
| ray | `cf-ray` 末三位 | 落到哪个 CF 机场 |

日常晨检跑 3 个代表页（`/`、`/5000years/`、`/collection/`），`--all` 跑全站 43 页。

## 二、结论：慢的不是站点

### 证据 1 —— 1.3KB 的静态文件也要 4~6 秒

`favicon.ico` 只有 **1360 字节**，纯 CDN 静态缓存，不经过 WordPress、不查数据库、不执行 PHP：

```
favicon  http=200  ttfb=4.60s  total=15.13s  size=1360
```

静态文件不存在"性能问题"。它慢，只能是链路慢。

### 证据 2 —— 所有请求都落在洛杉矶，且境外对照站同样慢

```
cf-ray: a4bd52fdee992f32-LAX     ← 三次采样全是 LAX
baidu.com        ttfb=0.13s      ← 本机网络正常，国内站很快
dash.cloudflare.com  15s 未连上  ← 出境方向整体拥塞
```

### 证据 3 —— TTFB 噪声 ±15 秒，绝对値不可信

同一批页面连续测，单次 TTFB 在 **2.9s ~ 23.1s** 之间乱跳，冷甚至比热还快（gap 为负），还出现超时 0 值。
这种噪声下，任何"本站 TTFB 是多少秒"的结论都是假的。**所以脚本改成了多采样取中位数，并把 TTFB 降级为参考値。**

### 证据 4 —— 站点自身该做的都做了

| 检查项 | 实测 | 判定 |
|---|---|---|
| 压缩 | 首页 219KB → **47KB**（Brotli） | ✅ 已开启，压缩率 78% |
| HTML 体积 | 各页压缩后 5~47KB | ✅ 正常 |
| HTTP 状态 | 200 | ✅ |
| 静态资源缓存 | CDN 命中 | ✅ |
| **HTML 缓存** | **DYNAMIC（每次回源）** | ⚠️ **唯一问题** |

## 三、唯一可优化项：HTML 每次都回源

`cf-cache-status: DYNAMIC` 意味着 HTML 不进 CDN —— 每个访客都要触发一次
「中国 → CF 洛杉矶 → GoDaddy 美国源站 → 原路返回」的完整往返。
而 favicon（命中 CDN）4.6s vs 首页（回源）10~16s，**中间那 5~10 秒就是这次跨太平洋往返**。

### 优化收益

把 HTML 放进 CDN 边缘缓存后，访客的首字节时间可以从「回源」水平降到「CDN 命中」水平。
静态资源已经证明这条路走得通 —— favicon 命中后是 4.6s，回源则要 10s+。
**这是本站目前唯一不改内容、不花钱、收益最大的性能杠杆。**

### 两个方案（都需你批准，我没有自动执行）

| | 方案 A：CF 缓存规则 | 方案 B：WP 端发缓存头 |
|---|---|---|
| 做法 | CF 后台 → Caching → Cache Rules，对 HTML 设 Cache Everything + Edge TTL | 子主题加 `Cache-Control: public, max-age=600` |
| 谁来做 | **你在 CF 面板点 5 分钟**（现有 API Token 只有 Analytics 只读权限，改不了 Zone） | 我改代码，但属 C 档（子主题）→ 需真机验收 |
| 生效范围 | 立即，可随时关 | 需传主题文件 |
| 风险 | 改完首页需清缓存才能看到更新 | 同上；且登录态页面不能缓存 |
| 推荐 | ⭐ **先做 A**，最干净、可逆 | A 不通再做 B |

**共同的注意事项**：缓存 HTML 后，改首页不会立刻生效（要等 TTL 或手动 Purge）。
建议 Edge TTL 设 **2 小时** 而不是 1 天 —— 本站更新不频繁，2 小时足够拿到绝大部分收益，又不至于改完干等。
**不要缓存** `/wp-admin/`、`/wp-login.php`、带 `wp-*` cookie 的请求 —— 缓存规则里要排除。

### 踩坑记录（照抄可省 40 分钟）

| 坑 | 报错 | 解法 |
|---|---|---|
| rule 里带 `name` | `unknown field "name"` | 单条 rule 只有 `description`；`name` 属 ruleset 顶层 |
| PUT 时带 ruleset `name` | `the name field cannot be modified: got X, want default` | 更新只发 `{"rules":[...]}` |
| `serve_stale` | `unknown field "disable"` | 免费版不支持，删掉 |
| `origin_cache_control`/`respect_strong_etags` | `not entitled to ...` | 免费版无权，删掉 |
| 🔴 **bypass 排前面** | 无报错，但 `/wp-json/` 照样三次 HIT | **Cache Rules 是 last-match-wins，bypass 必须排最后** |
| 首次 verify 全 MISS | — | 第一次请求必然 MISS，要预热后再取第二次 |
