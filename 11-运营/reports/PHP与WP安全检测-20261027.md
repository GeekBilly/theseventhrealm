# PHP / WordPress 安全检测 · 2026-10-27

> 触发：用户告知「最近 PHP 网站被爆出安全隐患」。
> 方法：① 公开情报检索（多国 CERT / CVE / 厂商公告）；② 对 `theseventhrealm.com` **只读**探测（GET 请求，不利用、不改任何东西）。
> 🔴 **本次检测的边界**：站点在 Cloudflare 后面且开了托管挑战，远程探测结果**不可作为"安全"的证据**，只能证伪/证实可公开访问的部分。

## 一、情报：本次爆的是什么

### 1.1 PHP2Shell（PHP 解释器级 RCE，非 WordPress 漏洞）

| CVE | CVSS 4.0 | 机理 |
|---|---|---|
| CVE-2026-109618 | 9.2 critical | 处理内存耗尽（OOM）条件时出错 → 内存破坏 → 执行恶意代码 |
| CVE-2026-109619 | 9.2 critical | 请求之间的失效内部状态会残留 → 在**后续请求**中执行恶意代码 |

- **触发方式**：发送特制 `multipart/form-data` HTTP 请求，**无需身份鉴别、无需登录**。
- **在野状态**：PoC 已公开；watchTowr 确认已出现针对两个 CVE 的利用尝试；Cloudflare 在官方补丁发布前就已观察到攻击流量并部署防护规则。截至目前**未公开确认**有具体服务器被成功攻陷。
- **修复版本**：PHP **8.5.12 / 8.4.27 / 8.3.36 / 8.2.35**（按你所在的版本分支升级对应版本）。
- **受影响**：8.5 ≤8.5.11、8.4 ≤8.4.26、8.3 ≤8.3.35、8.2 ≤8.2.34；**8.1 及以下已 EOL，没有官方补丁，必须升版本**。
- 🔴🔴 **关键认知**：这是 **PHP 解释器**的漏洞，不是 WordPress 的。北京大学通告写得很明确：
  > **仅更新网站插件、主题或框架不能修复本次漏洞。**

### 1.2 同一时间窗的 WordPress 插件漏洞（仅当装了才相关）

- **6 个 CVSS 9.8 未授权漏洞**（NVD 2026-10-16 发布）：My Calendar、Mang Board、MailOptin、ELEX HelpDesk、Theme My Login、Sunshine Photo Cart。NVD 只给"≤ 某版本"的上界，**未给出修复版本**，需查各插件页面确认。
- **在野利用的 XSS 后门战役**（CVE-2026-93836 WPC Product Bundles / CVE-2026-94504 Ninja Forms）：
  利用存储型 XSS 借管理员会话装恶意插件（伪装 slug `wp-smart-thumbnails`），**创建后台里看不见的管理员** + `?_wplogin=` 免密登录 + 文件管理器，并用 **mu-plugin** 持久化。
  ⚠️ **升级或删除插件都不能清除后门**；且文件时间戳被回写为站点的旧时间戳 ⇒ **按修改时间找可疑文件会漏**。

| 10 | 插件目录探测（12 个已知漏洞 slug） | 全部 403，**包括我编造的不存在的 slug** | ⚠️ **探测无效**，见下 |

### 2.1 关于第 10 项：我修正了一个错误判断

第一轮我看到 12 个漏洞插件全部返回 403，一度写成「存在但被拦」。

**这是错的。** 我做了对照实验：请求 `/wp-content/plugins/zzz-never-installed-xyz/readme.txt`（一个我随手编的、绝不可能存在的 slug），**同样返回 403**。

⇒ 结论：**403 是 Cloudflare / 服务器的统一拦截响应，不代表插件存在**。远程枚举插件这条路在本站**走不通**，必须用后台或 cPanel 确认。

同理，第 9 项那些"403"也不能解读为"文件不存在"——它们同样是被挑战了。**这两项都不能作为安全证据。**

## 三、需要你亲自动手确认的（我够不着）

| 优先级 | 动作 | 在哪做 |
|---|---|---|
| 🔴 **P0** | **查 PHP 版本**：cPanel → *Select PHP Version* / *MultiPHP Manager*。若低于 **8.2.35 / 8.3.36 / 8.4.27 / 8.5.12**（按所在分支）⇒ 立即升级；若还在 8.1 或更低 ⇒ 必须跨版本升级（EOL 无补丁） | GoDaddy cPanel |
| 🔴 **P0** | 升级后**重启 PHP-FPM / Web 服务**，并确认站点实际生效的版本（CLI 与 Web 可能不是同一个 PHP） | cPanel |
| P1 | **插件清单核对**：后台 *插件* → 对照一.2 的 8 个 slug，确认都没装；装了的升到修复版或直接停用 | WP 后台 |
| P1 | **入侵痕迹排查**：① `wp-content/uploads/` 下**不应有任何 `.php`**；② `wp-content/mu-plugins/` 是否有异常文件；③ 管理员数量是否与数据库一致（隐藏管理员在后台看不到）；④ 搜 `wp-smart-thumbnails` 与 `?_wplogin=` | cPanel 文件管理器 |
| P2 | 确认 Cloudflare **托管规则（Managed Rules）** 已启用并覆盖异常 multipart 请求 | CF 后台 |

## 四、若暂时无法升级 PHP：缓解措施（**不能替代补丁**）

按多国 CERT 的共识，按优先级：

1. **关闭会话上传进度**（最有效的一项）：在 `php.ini` / FPM 池 / 服务器配置里设
   `session.upload_progress.enabled = 0`，**然后重启所有 worker**。
   ⚠️ 必须在服务器配置层改，**不要**用 `ini_set()` 或 FPM 的 `.user.ini`（太晚，请求已经解析完了）。
2. **消除可控的内存上限失败**：`memory_limit = -1`，建议用 FPM 的 `php_admin_value`（应用层改不回去）。
   注意这**不能**根治——底层分配失败仍可能走到漏洞路径。
3. **收紧上传**：不需要上传的站点设 `post_max_size = 8M`；需要上传的设 `32M`，且 `upload_max_filesize < post_max_size`。在 Web 服务器/代理层限制请求体大小、multipart 分段数、字段数、嵌套深度（要覆盖没有 `Content-Length` 的请求）。
4. **阻断跨请求状态传递**（会掉性能）：FPM `pm.max_requests = 1`；mod_php 对应 Apache `MaxRequestsPerChild = 1`。
5. **PHP 8.5 专属**：`fatal_error_backtraces = 0`（只挡已确认的 fatal backtrace 路径）。
6. **WAF**：拦截异常 `multipart/form-data`。⚠️ 官方明确说 **WAF 单独使用不充分**。
7. **不要用** `RLIMIT_AS` / `RLIMIT_DATA` 代替内存限制——反而会触发漏洞路径的分配失败。

## 六、结论一句话

**WordPress 侧没发现可远程证实的问题；真正的风险点只有一个且未确认——PHP 解释器版本。** 这是唯一能导致"未登录就被执行任意代码"的项，而且它**不随 WordPress 更新而修复**，只能从 cPanel 升。建议今天就查版本。
