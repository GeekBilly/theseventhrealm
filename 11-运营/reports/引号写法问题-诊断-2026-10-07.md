## 二、根因：WordPress 的「智能引号」按英文规则转向，遇到中文就翻车

WordPress 有个 `wptexturize` 过滤器，会把源码里的 ASCII 直引号 `"` 自动转成弯引号，
称为 smart quotes。**它的开合判断是按英文写的**：看引号**前一个字符是不是空白**——

- 前面是空格 / 行首 → 判为**开**引号 `“`
- 前面是其他字符 → 判为**闭**引号 `”`

英文里 ` said "hello" ` 引号前面确实有空格，规则成立。
**中文里引号前面紧跟汉字，一个空格都没有**，于是 WP 把每一个都判成"闭合"——

```
源码：周公：把"天命"翻译成制度
        ↑ 前一个是「把」（汉字，非空白）→ 判"闭合"
线上：周公：把”天命”翻译成制度      ← 两个都成了右引号
```

### 实测证据（草稿页，验后已删）

同一份内容里三种写法同时提交，看 WP 保存后的实际字符：

| 源码写法 | WP 保存后 | 结果 |
|---|---|---|
| 半角 `"兼听则明"` | `”兼听则明”` | ❌ **两个都变右引号** |
| 全角 `「已经是全角」` | `「已经是全角」` | ✅ 原样保留 |
| 实体 `&#8220;…&#8221;` | `“…”` | ✅ 正确开合 |

**结论：WP 只改写 ASCII `"`。只要源码里写的是确定的 Unicode 全角字符（`“ ”` 或 `「」`），它就再也不动。**

### 为什么唯独「觉醒年代」页没事？看数据库里存的是什么

同一个接口取回两个页面的 `content.rendered`（**未解实体**），对比一目了然：

| | 字面 `“` | 字面 `”` | 实体 `&#8220;` | 实体 `&#8221;` |
|---|---:|---:|---:|---:|
| /5000years/juexing/ | **43** | **43** | 0 | 0 |
| /5000years/tang/ | 0 | 0 | **3** | **91** |

- 觉醒年代页存的是**字面全角字符**——WP 拿到 Unicode 弯引号后原样存取，所以它一直是对的；
- 唐代页存的是 WP **转出来的实体**，而且 91 个里只有 3 个是左引号。

左右 43:43 对 3:91，差别就是源码里那一个字符是全角还是半角。

> juexing 保持线上现状不动，免得把不知道差在哪的本地版本顶上去。

## 四、修复方向

**根治办法只有一条：本地源码里写确定的全角字符，不让 WP 猜。**

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 源码改全角引号 | 本地 16 个文件把 `"` 换成确定字符后上线 | ✅ 根治，一次到位 |
| B. 关掉 `wptexturize` | 子主题加一行 `remove_filter` | ❌ 中文正文里留着半角直筒子 `"`，宽度和开合都不对，更难看 |
| C. 不管，继续让 WP 转 | — | ❌ 现状即受损状态 |

技术上是安全的：`<ruby>` 那次已经证明该账号有 `unfiltered_html`，
REST 保存不过滤 Unicode  punctuation（53 处行内注音括号全数保留，就是现成的旁证）。
改造脚本可做成幂等 + 可逆，褪掉后逐字节还原原文。

## 五、待定：统一到哪一种？

修复时必须有一个统一口径，否则又会像现在这样三套并存。候选项：

| 口径 | 主张 | 站内先例 |
|---|---|---|

| **方头括号 `「」`** | 竖排/港台传统用法，方正，与书法调性搭 | 藏品页金句、总览页在用（153 处） |


## 七、修复力度为何要落在「本地源码」，而不是让 WP 继续转

既然根因是 WP 转错方向，能不能干脆继续用半角 `"`、让它转？不能——它的判断规则本身
就是错的（按英文空白判断），我们无法修正第三方逻辑。**唯一解是让它无可转**：
源码里写死的 Unicode 全角字符，WP 一个都不碰（第 3 节实测已证）。

所以修复的三条硬约束（都写进了 `11-运营/scripts/fix-quotes.py`）：

1. **开合靠顺序配对**（第 1/3/5… 个 → `“`，第 2/4/6… 个 → `”`），**不靠上下文猜**。
   上下文猜测正是 WP 翻车的那条路，不能重蹈覆辙。
2. **只动文本节点**：标签属性、`script`、`style`、注释、HTML 实体一概不碰（`href="#s2"` 安然无恙）。
3. **奇数个引号 → 整个文件跳过并报警**：有落单的说明内容本身有问题，顺序配对会全盘错位，不猜。

反向操作 `--strip` 可把 `“ ”` 换回 `"` 做回滚演练（奇数文件同样跳过）。

## 十、同源发现：`wptexturize` 连 ASCII 撇号也改写

发布后做「改动是否只落在引号字符上」的交叉验证时发现：

> 判定方法：把发布前备份的 rendered 与本地新源码各自去标签、去空白，**再去掉所有引号字符**，
> 两边应当逐字相同。若不同，说明改动里混进了非引号差异。

15 页中 14 页通过，**`yuan` 页有一处不同**：

```
备份（发布前线上）：Tuǒhuāntiěmù’ěr      ← U+2019
本地源码（当时）  ：Tuǒhuāntiěmù'ěr        ← U+0027 半角撇号
```

即 WP 也把 ASCII `'` 转成了 U+2019。**这次它转对了**——`'` 前面紧跟 `ù`（字母），
WP 的 apostrophe 规则在中文里同样成立，所以这里是歪打正着，线上显示一直是正确的 `’`。

但它留下一个隐患：**源码与线上不再是同一份**。下次谁从本地重发这一页，撇号就会退回直引号。

**处理**：把本地与该拼音所在的**源头词表**一并改成 U+2019，然后单独补发该页。

- `11-运营/data/注音词表-行内.csv` 第 41 行：`Tuǒhuāntiěmù'ěr` → `Tuǒhuāntiěmù’ěr`
  （⚠️ 只改页面不改词表，下次跑 `annotate-inline.py` 又会把它写回半角）
- `03-页面/朝代页/yuan.html` 同步，单页补发 #106 并验收通过
- 复核：线上 1 个 U+2019 / 0 个半角，本地同此，**两边一致**

## 十一、一句 reusable 的结论

> **WordPress 站点里，凡是会被 `wptexturize` 处理的 ASCII 标点，源码都应写成确定的
> Unicode 字符。** 第三方逻辑改不了（按英文规则判断），只能让它「无可转」。
> 由此也得出一条通用的发布后自检：
> **发布前备份 rendered 与本地源码，去标签去空白去引号后应逐字相同** ——
> 出现差异即说明改动混进了预期之外的东西，或源码本身已经漂移。
