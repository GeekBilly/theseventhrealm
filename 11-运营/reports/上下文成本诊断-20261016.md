# 上下文成本诊断（2026-10-16）

> 起因：用户反馈「每个任务的积分消耗变高」，怀疑是项目目录结构导致读取上下文过大。
> 结论：**主因不是文件夹结构，而是会话本身连续跑了 20.7 天未重建。** 结构有真实问题，但性质是「拖慢工具、逼出额外轮次」，不是「直接吃掉上下文」。

## 一、核心结论

| 归因 | 影响 | 性质 |
|---|---|---|
| 会话历史累积（20.7 天） | **主导因素** | 每发一条消息，整段历史随输入重发 |
| MEMORY.md + NOW.md 固定注入 | 次要但每天必付 | 每个新会话的「起步价」 |
| 4G 二进制素材导致全树扫描超时 | 间接 | 逼我用更多轮次 / 子代理 |
| 自产 813KB 归档 md | 潜在风险 | 一旦被 Read 命中就瞬间爆量 |

**工具使用本身是健康的**，没有发现「读了大文件」「输出爆量」的浪费：

- Bash 调用 3184 次，平均返回 **1 KB/次**
- Read 调用 916 次，平均返回 **2 KB/次**
- Write 300 次、Edit 1097 次、Grep 107 次
- 全会话**没有任何单次工具输出超过 100KB**

既然单次调用都不大，那么「越来越贵」就只能用一个原因解释：同一段历史的重发次数在增加。

### 结构问题的真实性质

**不是「文件太多读不完」，而是「全树操作不可行」。**

本次诊断中，`find` 扫全项目 **连续 3 次被超时杀掉（exit 137）**，全部死在 4G 的 `02-商品` 上。后果链条：

> 全树 find/Grep 超时 → 我被迫换更小范围的查询、或派子代理重来 → **产生额外轮次** → 每轮都带着那段 29MB 的历史重发 → 积分在轮次上被放大。

也就是说，素材体积通过「增加轮次数」间接放大成本，而这个放大器之所以致命，**仍然是因为会话太长**。两者是乘性关系。

### 一个自产风险点

`11-运营/reports/` 下有两份我们自己生成的超大 md：

- `MEMORY快照-202610-归档.md` 479 KB
- `MEMORY快照-202609-归档.md` 334 KB

合计 813 KB。它们是为 Git 备份而生的，目的正当，但**一旦被 Read 或宽范围 Grep 命中，单次就能吃掉可观上下文**。属于典型的「自己喂胖自己」。

## 五、优化方案

### A. 立竿见影（建议今天做）

1. **开新会话。** 同一项目目录、MEMORY 照常注入，但没有 20 天历史。这是唯一能立刻砍掉最大那块的动作。
2. **任务分批原则**：一个会话只做一个主题。跨主题就新开，需要回溯时靠 MEMORY.md 和 `11-运营/reports/` 的文档，而不是靠会话历史。
3. **收尾归档**：会话结束前让我把结论写进 `11-运营/reports/`，新会话靠读文档恢复上下文，成本从「几十 MB」降到「几十 KB 起步 + 按需读一个文档」。

### B. 降低「起步价」

固定注入 = MEMORY.md 14,952 字节 + NOW.md 13,280 字节 = **28,232 字节**，每次新会话都要付。

- NOW.md 13.3KB 是最大的可优化项（多为时效性状态，容易过期膨胀）
- 若要压，优先复审 NOW.md 是否还在描述当前状态；MEMORY.md 已压过多轮，再压有丢判据风险，建议维持

### C. 结构侧（收益较小但顺手）

1. **搜索禁区**：所有 `find`/`Grep`/`Glob` 默认排除 `02-商品`、`08-音频`、`99-归档` 的二进制子目录，避免超时。
2. **归档快照隔离**：建议将 `MEMORY快照-*-归档.md` 的生成产物改为 `.tar.gz` 或移出可被宽范围检索的目录。Git 备份已经在仓里，本地明文大 md 不必保留在 `reports/` 根目录。
3. **`find` 换代**：全树操作一律加 `-maxdepth` 或限定具体子目录（本次三次超时均为全树扫描）。

## 六、一句话判据

> **贵，是因为我在一个 20.7 天没重启的会话里干活；不是因为项目文件夹太多。**
> 每次感觉「同样的活变贵了」，先问会话年龄；每次想清理磁盘省积分，记住那 137MB 本来就不收费。
