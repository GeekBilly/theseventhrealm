# 平台文章发布格式与偏好（长期规则）

> **状态**：生效中 ｜ **建立**：2026-10-03 ｜ **适用**：知乎 / 小红书 / 公众号 / B站专栏 / 网站长文
> **一句话**：**只读加粗部分，也能读懂全文** —— 这是排版的第一目标。

---

## 一、总原则

| # | 原则 | 说明 |
|---|---|---|
| **P1** | **手机优先** | 一切以手机上能不能看清为准。长段落、宽表格、小字号一律砍掉 |
| **P2** | **加粗即导读** | 读者只看加粗，就能拿到全文骨架与结论 |
| **P3** | **每段最多一处加粗** | 加粗超过密度就等于没加粗 |
| **P4** | **平台原生优先** | 用平台自带的标题/引用/列表，不用花哨 HTML |
| **P5** | **不改事实、不吹身份** | 排版只改视觉，一个字不许改；不写自己没做过的事 |

---

## 二、层级规范（全平台统一）

| 层级 | 用途 | 格式 | 数量控制 |
|---|---|---|---|
| **L1 大标题** | 一、二、三…（章节） | **加粗** + 独立成行（知乎可用「标题」样式） | 每篇 4–6 个 |
| **L2 小标题** | 节内的一个点 | **加粗** + 独立成行 | 每节 0–2 个 |
| **L3 关键句** | **读者跳读时抓的东西** | **加粗**，连续不超过 2 行 | 每节 1–3 处 |
| **L4 引文** | 原文引用 | 「」内联 或 引用块 | 每节 ≤1 处 |
| 正文 | 其余全部 | 常规 | — |
| 数据 | 数字、年份、人名 | 常规（**不**加粗单个数字） | — |

### ⚠️ 加粗的三条禁令

```
① 不整段加粗（那是没加粗）
② 不连续加粗超过 2 行
③ 不为"好看"加粗 —— 每一处加粗都必须能独立成句、看得懂
```

## 三、「跳读测试」——发布前必做

> **把全文的加粗部分单独抽出来，连起来读一遍。**

**要求**：抽出来的那段，本身要能读通、且**不丢失核心结论**。

**示例**（知乎那篇秦灭六国）：

```
真正被低估的，是打完之后。
统一 8 年了，一个楚国小吏还在写「江陵公」
「书同文」根本不是改字形那么简单
不许叫猪，要叫彘
说白了就俩字：不用。
五十一年。不是五十一天。
秦的那套规范，连汉朝都没有全盘照接。
这些我查不到可靠来源，所以不写。
灭国是一瞬间的事。改掉一个地方"怎么办事、怎么叫、怎么写"，
是几十年的事 —— 而且改不干净。
```

**⇒ 这段单独读，全文的论点已经在里面了** ✅ 通过的才算排好版。

## 五、发布前检查清单（每次照做）

```
【排版】
□ 跳读测试通过（只读加粗能看懂）
□ 每段 ≤1 处加粗；没有整段加粗
□ 段落 ≤4 行（手机上）
□ 表格在手机上不横向滚动（宽表改列表）
□ 手机预览过一遍

【内容】
□ 一个字都没改（排版只动视觉）
□ 没有写自己没做过的事（不吹身份/经历）
□ 引文照原文，改述的地方不加引号
□ 查不到的量化数据，写「查不到」而不是编

【合规（P1-3）】
□ 不出现：真实姓名 / 单位 / 城市 / 收入 / 副业 /「卖」字
□ 外链：一篇 ≤1 个，用纯文本域名让平台自动识别（别手插超链接）
□ 署名口径：「个人创作者」
```

## 六、已知的平台坑（踩过记下来）

| 坑 | 现象 | 处理 |
|---|---|---|
| **知乎 Draft.js** | 塞 `innerHTML` 无效；`Cmd+V` 在 CDP 下不通 | ✅ 用 `agent-browser keyboard inserttext` 直接输入 |
| **中文后的直引号 `"`** | 平台自动排版（wptexturize）会把**开引号也转成右引号** | ✅ 源文里就写成 `“”`，别留直引号 |
| **知乎封面手机端会裁中间** | 主体内容放两侧 → 手机上被切掉 | ✅ **封面主体必须居中** |
| **手动插超链接** | 新号易被判营销 | ✅ 写成纯文本域名，让平台自己识别 |
| **知乎「修改」按钮前有零宽空格** | 按文字选元素选不中 | ✅ 选择器先清洗 `\u200b-\u200d\ufeff` |
| **嵌套标签用非贪婪正则删** | 只删掉外壳，内层标签留在页面上 | ✅ 必须按结构匹配，别用 `.*?` 整块删 |
| **markdown 表格粘贴到知乎** | 转纯文本后会留下 `---- ----` 这样的横线，非常难看 | ✅ **别用表格**。改成「一行一件事」的短句列表 |
| **双栏对齐（名词 + 解释）** | 靠全角空格对齐，手机上必然错行，最费眼 | ✅ 拆成两行，或直接写成一句话 |
| **shell 循环处理含空格的字符串** | `for x in $(...)` 按空格切词，中文标题被切碎 | ✅ 用 Python 驱动，不走 shell 拼接 |
| 🔴 **改内容时丢掉外层容器/样式块** | 我用"新头 + 从某锚点往后"的方式拼装 WordPress 页面，结果把原文**头部的 `<style>` 与外层 `<div class="sr-collection">` 整段丢了** → 页面上 CTA 变成**裸链接**、栅格和价格样式全失效。**第二次犯同类错误**（第一次是清空知乎编辑器抹掉格式） | ✅ 改前先定位**外层容器与样式块的边界**；<br>✅ 改后必须验「**样式类还在不在**」（如 `sr-collection`、`class="cta"`），不能只验文字；<br>✅ 拼接式改写后，**逐项比对 div 开合、style 块数量、锚点是否重复** |
| 🔴 **清空重填编辑器 = 抹掉所有格式** | 加粗和链接**全部消失**（我因此在知乎那篇上返工两次，最后一次还忘了补链接） | ✅ **改文字必须在加粗/加链接之前做完**；<br>✅ 顺序固定为：**定稿 → 填入 → 加粗 → 加链接 → 复核 → 发布**；<br>✅ 每次重填后，加粗与链接都要**重新做一遍并复核** |

## 七、本规则的由来

用户 2026-10-03 提出：

> 「文章里的文字如果是段落标题还有一些重要的句子可以变一下字体么？整个文章通篇下来都是一个格式未免太平淡，可以把重点的句子和题目标识一下，给不想看太长的人可以把非加粗加黑的跳过也不影响理解文章的那种。」

**⇒ 由此确立 P2「加粗即导读」与第三节「跳读测试」** ✅

同日追加（用户反馈）：

> 「这里的格式要改，太难看懂了，简单点，清晰点，分行。」

**⇒ 另立一条操作顺序**（血泪教训）：

```
① 定稿（文字一个字不再动）
② 填入编辑器
③ 加粗
④ 加链接
⑤ 复核（加粗数 / 链接数 / 字数）
⑥ 才允许发布
```

⚠️ **顺序不能颠倒** —— 只要在加格式之后再改文字，就得从第 ③ 步重来。

**⇒ 由此确立「一行一件事」**：不用表格、不用双栏对齐、不用冒号破折号凑格式。
**一条信息一行，短句，读起来不用回头找对齐。** ✅

## 八、出图工具坑（PIL）

| 坑 | 现象 | 正解 |

| 🔴 **`alpha_composite` 静默丢弃负坐标贴图** | 拼贴式水印整层为空（alpha 全 0），**不报错**，最难查 | ✅ 负坐标一律用 `paste(im, (x,y), im)` |

**⇒ 通用教训**：图像处理里**"没报错" ≠ "画上了"** —— 必须**量像素**验证（和字体回退那个坑同一类）。

## 九、逐帧渲染动画的工具坑（2026-10-04 实录）

| 坑 | 现象 | 正解 |
|---|---|---|
| 🔴 **用 `animation-delay` 做时间轴** | 逐帧截图时**画面全空** —— CSS 动画的 delay 从**页面加载**算起，而我们每秒开一个新页面，"13 秒后开始"永远到不了 | ✅ **把画面状态写成 `t` 的函数**，每帧独立计算；**不要用 CSS 动画做时间轴** |
| 🔴 **多个 Chrome 共用 `--user-data-dir`** | 6 个并行抢 6 个目录 → **互相锁死**，90 秒超时，336 帧只出了 8 帧 | ✅ 每个线程**独占**一个 profile 目录（`threading.local()`） |
| 🔴 **并行开多个 Chrome 本身就会锁死** | 单帧 ~5 秒（能跑），4 个并行 → **全部超时** | ✅ **开一个 Chrome，用 `agent-browser` 逐帧驱动 page 里的 `renderAt(t)`** —— 287 帧 6 分 47 秒跑完 |
| 帧缺口 | 288 帧里缺 1 帧 → ffmpeg 会**在那里停住** | ✅ 合成前先查缺口，**用前一帧复制补上**（视频里看不出来） |

**⇒ 通用教训**：**"没报错" ≠ "画上了"**（水印那次）、**"动画写了" ≠ "会动"**（这次）——
凡是不确定的地方，**看一帧**或**量一次像素**，比读代码快得多。

## 十、混音验证方法（2026-10-04 实录）

**问题**：怎么在**听不到**的情况下确认「配音真的混进去了、而且在正确时刻」？

### ❌ 失败的三种测法

```
① 直接比「混音 vs 纯音乐」—— 基线取错：音乐被压过、混音被 loudnorm 提过，差值无意义
② 给对照也过同样的 loudnorm —— 仍有残差：loudnorm 是动态的
③ 用 silencedetect 找静音段 —— 音乐是连续的，根本没有静音段
```

### ✅ 能用的办法：**残差法**

```
让【对照 = 音乐×同一增益】走过【完全相同的链】，
再从成品里逐样本相减 → 残差就是纯人声
然后按 0.5 秒窗算 RMS，>阈值 的连续段就是人声所在

关键前提：链里【不能有动态处理器】
   ⚠️ loudnorm / alimiter 会改变整条波形 → 残差到处都是（实测 0–74s 全是"人声"）
   ✅ 只用固定增益 volume=… → 残差干净，三段人声一目了然
```

**⇒ 由此定一条工程规矩**：**要可验证，就别在验证路径上放动态处理器**；
限幅只放在**最后一道**（且只影响峰值，不影响 RMS 对比）。

### 混音电平的判据

```
人声要比音乐【高 5 dB 以上】才叫"清晰可闻"
（实测：只高 0.4–2.0 dB 时完全被压住；调到 +5.6~6.8 dB 才对）
```

## 十一、宣传片的声音（2026-10-04 用户定案）

**结论：默认【纯背景音乐 ＋ 竖排字幕】，不加人声。** 用户原话：
> 「感觉声音和音乐不配，声音太生硬了，不是专业的，还是纯背景音乐吧」

**为什么这是对的选择（不是妥协）**：
```
① 念古文极难 —— 古人说话没有录音，现代人怎么念都有点"端着"
② 低沉的水墨画面 ＋ 人声 → 容易变成纪录片解说腔
③ 竖排字幕让观众【自己读】，代入感比听人念强
④ 纯音乐版也更省事：改词不用重录、不用重混
```

**⇒ 以后的规矩**：
```
· 宣传片默认【纯音乐＋字幕】
· 要加人声必须单独论证：谁念？为什么非人声不可？
· 人声素材可以留作【商品版】（动态壁纸）或【家人版】——那里曝光小
```

**技术副产品**（可复用）：
```
· 三条台词的清理链：highpass=85 + afftdn 降噪 + agate 门限 + silenceremove + loudnorm
· 混音验证的【残差法】见 §十 —— 听不到音频时也能确认人声位置与电平
```

## 十二、🔴 agent-browser 的 socket 目录必须【一会话一目录】（2026-10-04 实录）

**事故**：宣传片渲染到一半，我为另一件事（开 B站）执行了
`export AGENT_BROWSER_SOCKET_DIR=<同一个目录>` + `connect <另一个端口>`，
**把正在跑的渲染会话的连接顶掉了** →
渲染后半段（54.3s–73s，449 帧）**截图截到了 B站 网页** 🔴

**根因**：`agent-browser` 用 **socket 目录**保存"当前连的是哪个浏览器"。
**同一个目录只能有一个活跃连接**，后来的会顶掉先前的。

**⇒ 规矩**：
```
· 每个并发的浏览器会话，用【各自独立】的 socket 目录
    渲染      →  .agent-browser-render
    B站       →  .agent-browser-bili
    知乎      →  .agent-browser
· 尤其：后台长任务（出帧、批量截图）在跑时，
        绝不要在它用的那个目录里 connect 别的端口
```

**⇒ 检测办法**（这次靠它定位）：B站 页面有很强的品牌蓝，
对成品逐帧扫 `蓝>150 且 蓝-红>60` 的像素占比，>6% 即判定该帧被污染。

**⇒ 修复代价**：只需重渲被污染的那一段（496 帧约 6 分钟），
**不必整条重来** —— 所以**逐帧渲染的好处是"可局部重跑"**。

## 十三、Cloudflare 免费版的硬限制（2026-10-04 实测）

**撞到才知道的，记下来免得下次再试**：

| 项 | 免费版限制 | 报错原文 |
|---|---|---|
| 限流周期 | **只能用 10 秒** | `not entitled to use the period 60, can only use a period among [10]` |
| 封禁时长 | **只能用 10 秒** | `not entitled to use a mitigation timeout different from 10` |
| 限流特征 | **必须包含 `cf.colo.id`** | `characteristics field is missing 'cf.colo.id', this is required as ratelimiting counting is processed at colocation level only` |
| 托管规则 | 需付费 | 界面显示 `Upgrade plan` |
| 额度 | 自定义规则 5 条 · 速率限制 1 条 | — |

**API 建规则的三个坑**：
```
① PUT /zones/{id}/rulesets/phases/{phase}/entrypoint
   请求体【不能带 kind 和 phase 字段】—— unknown field 报错
② phase 名是 http_ratelimit（不是 http_request_ratelimit）
③ 读 entrypoint 用 GET，若 ruleset 不存在会报
   10003 could not find entrypoint ruleset —— 用 PUT 创建即可
```

**⇒ 用 API 比点 SPA 可靠得多**：CF 后台每次交互都重渲染，
脚本点击经常落在失效节点上（本次自定义规则在网页上点了 8 轮没成，
改用 API 一次成功）。

## 十四、🔴 bash：未加花括号的变量紧跟中文会炸（2026-10-04 实录）

**症状**：
```
11-运营/scripts/install-cf-security-job.sh: line 58: PLIST?: unbound variable
```

**错在哪**：
```bash
echo "  ✅ 已写 $PLIST（$(wc -c < "$PLIST") 字节）"
                 ↑
# 想输出「已写 <路径>（123 字节）」
# 但 bash 把「PLIST（」整个当成变量名了 ——
# 全角括号（U+FF08）是多字节字符，bash 的变量名扫描一直吃到它。
# 变量名 PLIST（ 不存在，遇上 set -u 就立刻退出。
```

**正解**：**变量后面只要跟非 ASCII 字符，一律加花括号**
```bash
echo "  ✅ 已写 ${PLIST}（$(wc -c < "$PLIST") 字节）"
```

**⇒ 顺带定一条规矩**：
```
本仓库的 .sh 脚本，交付前必须跑一次
    bash -n 脚本.sh
（这次漏了。脚本涉及 ~/Library/LaunchAgents 之类沙箱写不了的地方，
  无法端到端试跑，但 bash -n 是随时能做的、零成本的语法检查。）
```

**批量自检命令**（找同类隐患）：
```bash
grep -nE '\$[A-Za-z_][A-Za-z0-9_]*[（）：，。、「」【】·…]' *.sh
```

## 十五、⚠️ 验证「文件是否已删」必须破缓存（2026-10-04 实录）

**差点误判**：用户在 cPanel 删掉了 `legacy-book-club` 和
`seventhrealm-child-fixed-20261002`，我立刻去验，两个都返回 **200** ——
看起来"没删成功"。加了缓存破坏参数再验，两个都是 **404** ✅

```
响应头坐实：
  cf-cache-status: HIT        ← 200 是 Cloudflare 缓存给的
  age: 5150 / 6439            ← 缓存里躺了 1.4–1.8 小时
  cache-control: max-age=14400（.css 缓存 4 小时）
```

**⇒ 规矩：验证线上文件存在与否，URL 一律带随机参数**
```bash
curl -o /dev/null -w '%{http_code}' "https://theseventhrealm.com/path/file.css?cb=$RANDOM$RANDOM"
```

**⇒ 同理适用于**：
```
· 验证主题/插件文件是否已删或已替换
· 验证改动是否上线（尤其是 .css / .js / 图片，被 CF 缓存）
· 验证上传的新版本是否生效
（HTML 页面一般不缓存，但带 .css/.js/图片后缀的静态资源会被缓存 4 小时）
```

**⇒ 反过来也要记住**：**删掉的文件在 CF 缓存过期前（最多 4 小时）仍可被外部访问到**。
对已废弃的第三方主题来说风险很小，但如果删的是**含敏感信息的文件**，
必须去 Cloudflare 后台「缓存 → 清除缓存」手动清一次。

## 十六、CF 建 301 跳转：Redirect Rules 建不了就用 Page Rules（2026-10-04）

**场景**：把 `tantse.com` 301 跳到主站。

```
❌ 首选路径（CF 新版）：Redirect Rules
   PUT /zones/{id}/rulesets/phases/http_request_dynamic_redirect/entrypoint
   ⇒ 一直报 "request is not authorized"
   ⇒ 给 token 加了 Config Rules:Edit、Zone:Edit、DNS:Edit 之后【仍然不行】
   ⇒ CF 的权限列表里也【没有 "Dynamic Redirect" 这一项】

✅ 退路：Page Rules（一次成功）
   POST /zones/{id}/pagerules
   {
     "targets": [{"target":"url","constraint":{"operator":"matches","value":"tantse.com/*"}}],
     "actions": [{"id":"forwarding_url","value":{"url":"https://目标.com/$1","status_code":301}}],
     "priority": 1, "status": "active"
   }
   ⇒ $1 会捕获路径，查询参数默认保留 ✅
   ⇒ 免费版额度 3 条
```

**⚠️ 注意事项**：
```
· Page Rules 是 CF 旧功能，官方已宣布逐步淘汰 —— 能用但别长期押注
· Redirect Rules 那条路的权限问题【没有查明根因】，将来迁移时要重新研究
· DNS 要有一条 proxied 记录（占位 IP 192.0.2.1 即可），
  否则流量到不了 CF，跳转规则再对也没用
```

## 十七、⚠️ 换图后"看起来没变"要排两层缓存（2026-10-05 实录）

**事故**：8 朝壁纸换新上线后，用户说「藏品页的前四个朝代的图不对啊」。
我一查：**文件层面完全正确**（线上图片与本地新版 sha256 一致、生成时间正确、
内容与成品吻合）。最后是**浏览器缓存** —— 用户 Cmd+Shift+R 后正常。

**⇒ 两层缓存，缺一不可**：
```
① Cloudflare 边缘缓存（.jpg/.css/.js 默认 max-age=14400，即 4 小时）
   排除方法：请求时带随机参数
     curl "https://站点/xxx.jpg?cb=$RANDOM$RANDOM"
   或用 CF API 清缓存

② 浏览器本地缓存
   排除方法：Cmd+Shift+R（Mac）/ Ctrl+F5
   ⚠️ 这一层脚本查不出来 —— 只能靠用户强刷，或改文件名
```

**⇒ 判断顺序（省时间）**：
```
1. 先比 sha256：线上文件 == 本地新版？
   · 相同 → 不是文件问题 → 让用户 Cmd+Shift+R
   · 不同 → 再看响应头 cf-cache-status
              HIT  → 是 CF 缓存 → 等过期或清缓存
              MISS → 是部署问题 → 查上传/替换链路
```

**⇒ 更彻底的规避**：**改文件名**（如 `shang-site-v2.jpg`）
```
两层缓存同时失效，用户无需强刷 ✅
代价：页面引用要跟着改（我们本来就在改页面，成本很低）
⇒ 下次大批量换图时优先用「换文件名」而不是「同名覆盖」
```

## 十八、CF 免费版表达式运算符限制（2026-10-05 实测）

给站点上三层 WAF 规则时撞到的：

| 运算符 | 免费版 | 报错 |
|---|---|---|
| `eq` / `contains` | ✅ 可用 | — |
| `ends_with` | 🔴 **根本没有这个运算符** | `expected ComparisonOp` |
| `matches`（正则） | 🔴 需 Business 套餐 | `not entitled: the use of operator Matches is not allowed, a Business plan or a WAF Advanced plan is required` |

**⇒ 替代写法**：用 `contains` 代替 `ends_with` / `matches`
（例如 `.sql` 结尾 → 退而用 `contains ".sql"`，略宽但免费版够用）

## 二十一、🔴 浏览器：一个实例 + 多个标签页（2026-10-05 用户定规）

**用户原话**：「你可以开一个浏览器多个标签页」

**事故背景**：2026-10-05 一天之内，为做 CF / B站 / 百度 三件事，
陆续起了 5 个独立的 Chrome profile，共 42 个进程。
用户的 Mac 只有 **8 GB 物理内存**，交换被吃到 **17 GB**，
内存压力长期黄色 → 整机变慢。

```
清理前后：
  agent-browser 临时实例 10 ｜ bilibili 9 ｜ baidu 7 ｜ zhihu 7 ｜ 用户自己的 9
  清理后只剩用户自己的 9 个 ✅（关掉 33 个进程）
```

**⇒ 规矩（以后一律照做）**：
```
① 全程【只开一个 Chrome 实例】，用 --remote-debugging-port 起
② 不同任务【开新标签页】，不用开新实例
   · agent-browser open <url> 会复用当前连接的浏览器
   · 多任务之间用标签页切换，不要 connect 到别的端口
③ 一个任务做完，关【标签页】，不关浏览器
④ 全部做完，再关那【唯一一个】实例
⑤ 用完顺手删 profile 目录（/tmp/*-prof 也要清）
```

**⚠️ 与此并存的另一条规矩（§十二）**：
```
如果确实必须同时跑两个浏览器会话（例如一个在跑长任务、另一个要交互），
则【必须用各自独立的 socket 目录】（.agent-browser-xxx），
否则后 connect 的会顶掉先前的连接 —— 那次的代价是 449 帧宣传片报废。
⇒ 但那是【例外】；默认仍是一个实例多标签。
```

**⚠️ 硬件现实**：
```
本机 8 GB 物理内存，跑不动「WorkBuddy + DeepSeek Harness + Chrome」三件套：
  WorkBuddy        约 5.9 GB
  DeepSeek Harness 约 2.0 GB
  ⇒ 两件就吃满全部物理内存，Chrome 只能全走交换
建议：不要在 DSH 会话进行中同时开着 WorkBuddy 做重活；
     或长期看，这台机器需要加内存（若可升级）。
```
