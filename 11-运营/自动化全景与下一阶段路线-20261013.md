### 1.3 gitsync 的现状说明（2026-10-13 实测）

```
原计划：launchd 每日 02:30 跑 qj-sync.sh auto
实际踩到三件事：

① 脚本在 launchd 下会崩
   launchd 用 `sh` 调起脚本 ⇒ zsh 进入 sh 兼容模式 ⇒ ${0:A} 被当成未定义变量 A
   ⇒ "A: unbound variable"，一次都没跑成功（err 日志里只有这一行，stdout 全空）
   ✅ 已修：改成 POSIX 写法（dirname + pwd），sh / zsh 两种调用都能跑

② 我这边能 kickstart，但 load / bootstrap 都失败（Load failed: 5 / Bootstrap failed: 5）
   ⇒ 尝试用新 plist 重载时 bootout 成功、bootstrap 失败 ⇒ 任务一度掉线
   ⇒ open .command / osascript 让 Terminal 代跑，在本环境都触发不了

③ 曾经的过渡方案：WorkBuddy automation（每日 02:30）——**2026-10-16 已撤销**。

   ✅ **当前主方案（10-16）：Git 同步并入每日晨检**，一天跑两次：
      【负一】05:00 开工落盘（取代原 02:30）＋【六】收尾落盘（推走晨检产物）。
   理由：① 晨检产物当天进 Git，不再等次日 02:30（原延迟约 21.5 小时，`站点数据.csv` 断一天就永久缺失）；
      ② 少一次会话唤醒（10-16 实测每次起步价约 20K 固定系统提示 ＋ 6.3K 记忆注入）；
      ③ 晨检内两次同步互为保险——即使后段中断，开工那次已把改动推走。
   ⚠️ 连带动作：**mini 端 `backup-pull` 已从 03:00 改到 06:30**（用户 10-16 已改完）⇒ 时序恢复正确：MacBook 05:30 push → mini 06:30 pull。

冗余保险：若你想 launchd 也跑，在 Finder 里双击
   `11-运营/scripts/装载-每日同步任务.command`（它会 unload → load → 试跑 → 显示日志）。
   两套并存不冲突（第二个跑时发现已是最新就跳过）——但现在已非必需。
```

## 二、五条天花板（先认清边界，再谈自动化）

### 1. 会话制，不是常驻进程
Automation 每次是**唤醒一个新会话**，跑完即散。跨会话状态只能靠文件
（`.workbuddy/memory/` + `11-运营/data/*.csv` + 项目文档）。
⇒ 所以"自动化"的实质是：**定时唤醒一个会读项目文件的 agent**。
这也意味着——**项目文档写得越清楚，自动化越聪明**；文档没写的，它每次都会重新猜。

### 2. 沙箱无权注册常驻任务
`launchctl load` / `crontab` 在沙箱里都起不来（`Load failed: 5`）。
⇒ 真正常驻的东西只能靠 **automation（云端定时）+ 用户手动装的 launchd** 两条腿。

### 3. 云端页面连不到本机
浏览器规则决定了资料库/云端的页面**连不上 127.0.0.1**。
⇒ 放资料库的工作台**永远是快照**，要更新就得重新导出一份（见 `11-运营/exports/`）。
⇒ 真要"云端自动更新"，只能由服务端定时跑完再同步上去——而 `--auto-upload` 在 launchd 环境下
   `E_AUTH_FAILED`，目前**实际只能手动同步**。

### 4. 平台侧没有开放接口
- **淘宝**：开放平台 API 需企业资质/ISV 授权，个人店拿不到 ⇒ 只能靠本机 CDP 读卖家后台页面
  （`cdp-page-read.mjs` + 已登录的 Chrome profile）。**读可以，"操作"风险自担。**
- **Cloudflare Analytics**：免费版只能回溯 3–4 天 ⇒ 断采一天永久缺一天，这是每日晨检必跑采集的原因。
- **千牛/旺旺**：自动回复、快捷短语是**平台侧能力**，比我们自己做机器人可靠得多，优先用它。

### 5. 我们自己的红线（比平台规则更硬）
- 🔴 **加油站签到严禁自动化**（P0）：超额积分回收、严重者限号 ⇒ 只能提醒，不能代签。
- 🔴 **四类改动先出申请单**：发布上线／改线上内容／模板变更／涉合规金钱 ⇒ 一律不得自动执行。
- 🔴 **R-19 在职金融从业**：不虚构主体、不露职业身份；客服口径只能是「一个个人创作者」。
- 🔴 **失败一次即降级**，严禁重试循环（成本优先于完整性）。

## 三、四层分级（新自动化一律先对号入座）

| 层 | 定义 | 项目里的具体动作 |
|---|---|---|
| **L0** 全自动 | 只读采集 / 本地生成 / 备份，做错了也无外部影响 | 站点体检、积分日额、CF 采集、DeepSeek 记账、改动评审、看板同步、Git 同步、市场风向 |
| **L1** 自动备料 → 人一键 | 生成草稿/工单/包裹/话术，**不对外发出** | 社区发文草稿、上线执行申请单、订单包裹与交付话术、客服回复草稿 |
| **L2** 必须本人 | 涉及对外生效、身份、金钱承诺 | 最终点发布、扫码登录、退款与任何对买家的承诺、加油站签到、改价 |
| **L3** 永不 | 违规或失真 | 改价删评、代客操作账号、虚构主体资质、绕过平台规则、编造数据 |

## 四、成交交付：能做到哪一步

### 4.1 已确认走不通的两条（2026-10-11 已查证，见 `04-市场/03-推广获客/淘宝发货自动化方案-20261011.md`）
- ❌ **电子交易凭证**：O2O 线下核销功能，需「核销门店库」，我们没有 ⇒ 还得**取消勾选**
- ❌ **官方自动发货**：面向卡密类商品，我们的「设计素材/源文件」类目不在支持列表

### 4.2 ⭐ 可落地的「订单雷达 + 一键打包」（L1，性价比最高）

```
① 定时扫描：CDP 读卖家后台「已卖出的宝贝 / 待发货」
     → 输出待发货清单（订单号 / 商品 / 规格朝代 / 下单时间 / 距 24h 承诺还剩多久）
② 自动打包：按规格调 pack-listing-assets.py 生成对应 zip
     → 单朝 ¥12 = 该朝 3 档 + 手机 2 张；四辑 ¥39 = 该辑 4 朝
③ 生成话术：套《淘宝发货自动化方案》§三 的短语模板，填好朝代名
④ 推送给你：只输出「N 单待发 + 包裹路径 + 复制即用的话术」，不替你点发货
⑤ 你点：千牛粘贴话术 → 拖 zip → 发送 → 后台点「无需物流」发货
```

实际耗时目标：**30 秒/单**，与现在的纯手工方案一致，但**不用自己找文件、不用自己拼话术**。

⚠️ 前提与风险（动手前必须先验证）：
- **订单页能否稳定读取未验证** —— 目前只用 CDP 读过商品编辑页，订单列表的 DOM 结构需实测
- 🔴 **绝不自动点「发货」/「同意退款」**：超时和误操作都是违规账，必须人点
- 常驻 Chrome 的登录态会过期，脚本要能识别「未登录」并退化成提醒，而不是乱点
- 每日扫描次数要少（建议 2 次），CDP 反复读后台本身就是风险信号

### 4.3 客服：走平台侧 + 草稿库，不做自动发送机器人

```
平台侧（优先，零维护）：千牛自动回复 + 6 条快捷短语 + 关键词回复
                       ⇒ 覆盖「欢迎语 / 离线 / 怎么用 / 退款说明」80% 的问法
我们这侧（L1）：       客服草稿库 —— 按问题类型匹配标准答复草稿，
                       输出给你「复制即用」，你确认后自己发
永不（L3）：           机器人直连千牛自动发送
```

理由：客服回复是对外的**实质承诺**（退款、授权范围、交付时间），
一旦自动发出错误口径，风险远大于省下的几十秒。

## 六、成本纪律

- 每个 automation 跑一次 = 一次会话成本 ⇒ **新增前先估它每月跑几次**
- 同频任务合并（现在晨检一个 automation 里塞了 7 件事，就是这个道理）
- 失败一次即降级，日志写「本次未能自动获取」，**绝不重试、绝不编造**
- 只读优先：能读 CSV 的不要联网，能本地跑的不要上云
