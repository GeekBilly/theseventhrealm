# 每日上线评审流程（v1 · 2026-09-30）

> 目标：**每天把空间里新产生的改动拉出来一次**，分出「哪些会影响到线上」，由你拍板是直铺、先看一眼、还是先跑测试环境——不再等到攒一堆才发现没人记得改了什么。
> 配套脚本：`11-运营/scripts/daily-change-review.py`（挂在每日晨检里自动跑）。

---

## 一、数据源与可信边界

改动清单来自 WorkBuddy 本地变更索引 `~/.workbuddy/changes-index/*.json`：每条记录含 `filePath / action(create|modify|delete) / additions / deletions / createdAt`。

- **优点**：零联网、零积分、含增删行数，能区分「新建 / 改动 / 删除」。
- **边界**：它记录的是**文件被改写过**，不代表「可以发布了」。这就是为什么还需要人拍板。
- 本项目**没有 git**，所以内容级 diff 只能看行数，不能直接看差异文本；需要细看时单独问我 `diff`。

---

## 二、每天在晨检里做什么（自动）

```
跑 sync 之外：python3 11-运营/scripts/daily-change-review.py --hours 24
→ 输出 11-运营/reports/每日改动评审-<日期>.md  +  晨检正文里给摘要
```

脚本做三件事：

1. **拉改动**：窗口内所有文件变更，按目录分成
   - 网站设计·可上线（`03-页面/`、`seventhrealm-child/`、`05-发布包/`）
   - 产品资产（`02-商品/`、`06-品牌/`）
   - 内容稿件（`01-内容/`）
   - 市场推广（`04-市场/`、`09-社区/`）
   - 运营与工具（`11-运营/`、`10-规划/`、`07-课程/`、`08-音频/`）
2. **压噪声**：上线类全列，其余每类只列改动量 Top 8，剩下的折叠成「另有 N 个文件（累计 +X −Y）」。（实测一天能改 200+ 个文件，不折叠等于刷屏。）
3. **给档位**（只对「会影响线上」的文件）+ **下游联动提示**（改了上游别忘了跑下游）。

## 三、三档判定规则

| 档 | 触发条件 | 含义 | 处置 |
|---|---|---|---|
| **A 可直接铺** | 文本级小改（增删 ≤30 行），或已上线同类朝代页的小幅改动（≤80 行且结构未变） | 风险低 | 体检通过 → 直接发 |
| **B 先本地预览** | 新增页面、或改动量较大的页面 HTML | 看一眼再决定 | 本地渲染 → 我看/你看 → 通过后发 |
| **C 需真机验收** | 动了 `seventhrealm-child/`（含 .css/.php）、或整包 `05-发布包/*.zip` | 一改影响全站，且主题包上传是稀缺操作 | 必须先在测试环境跑一轮 |

> 判定是脚本给的建议，最终以你的判断为准；你觉得该升档就升档。

## 四、测试环境：现状与可选方案

**现状（2026-09-30 实测）**：`staging / test / dev` 三个子域 DNS 均无解析记录（dig 为空）→ **目前没有任何真机测试环境**。所以现在「先测」只有两条替代路径：

| 方案 | 能验到什么 | 验不到什么 | 成本 |
|---|---|---|---|
| **① 本地静态预览**（现有能力，零成本） | 页面本体结构、字体/排版/水墨样式、文案 | WP 主题的页头页脚包裹、导航高亮、手机端真实容器 | 0 |
| **② WP 草稿 + 后台预览**（推荐升级） | 主题包裹、导航高亮、真实渲染链路 | 需要你在后台点一下 | 一次性配置，之后每次 1 分钟 |
| **③ cPanel 子域 staging**（需你在主机后台操作一次） | 完整真机，与线上同环境 | — | 主机资源 + 你操作一次，之后自动用 |

**建议路线**：先用 ①+②，暂时不建 ③。理由——现在每月上线次数是个位数，为主机再起一套 WP 的收益不足以覆盖维护成本；真到要动导航/主题那类全站改动，用 ② 已经能看到 90% 的问题。等你确认要频繁改版了，我再出 ③ 的操作清单（cPanel → 子域 → 装 WP → Cloudflare 加子域橙云）。

**② 的具体做法**：
1. 我用 REST 发布一篇 `status=draft` 的草稿（不动线上任何已发布页）；
2. 你在 WP 后台 → 页面 → 找到草稿 → 点「预览」；
3. 你确认 OK → 我再把它 `status=publish` 转正（或更新到目标 ID）。
   ⚠️ 前提：目标页面是**我（MollyBot_No.2）自己创建的**；别人建的已发布页（如旧「联系我们」id=28）我改不动，那类只能你在后台手改。

## 五、上线前的固定动作（不可省）

### 第 0 步（2026-09-30 新增）：先判定「到底该不该发」

**假警报已经出现两次**：一次是子主题本地改过但内容早已随 v1.6 上线；一次是 16 朝页本地与线上实质完全相同。所以**在备份之前**，先用内容比对器确认确实有差异：

```bash
# 16 朝页批量
python3 11-运营/scripts/live-diff.py --parent 32 --dir 03-页面/朝代页
# 单页 / 加 --verbose 看差异样本
python3 11-运营/scripts/live-diff.py --map "32:5000years" --verbose
```

- 退出码 **0** ＝ 线上已是最新 → **不要发**，重传既无收益还担风险。
- 退出码 **1** ＝ 有实质差异 → 继续下面第 1–4 步。
- 退出码 **2** ＝ 取数失败（通常是 401 凭据失效）。

它做三层归一化，专门消除 WordPress 造成的「看起来不同其实一样」：`wpautop` 补的 `<p>`、`wptexturize` 把引号美化成的 `”`、HTML 实体。已用 WP `content.raw` 逐字节比对验证过结论可靠（16/16 一致）。

```
1. 11-运营/scripts/backup-site.sh          # 备份当前线上（回滚的唯一依靠）
2. 发「执行申请单」给你                 # 关键改动必须批准，不自作主张上线
3. 你批准后执行：
   - 单页：   11-运营/scripts/publish-page.sh
   - 法务页： 11-运营/publish-pages.sh
   - 朝代页： 11-运营/朝代页流水线/publish.sh（parent=32）
   - 主题包： 攒一批上传
4. bash 11-运营/scripts/site-health-lite.sh # 发布后全站 URL 状态码复核
```

**发布前必做的三项体检**：
- 私密信息扫描（手机号 / 个人邮箱 / 真实姓名）——`publish-pages.sh` 内置，跑 connector 时会拦。
- 新页结构是否与线上同类页一致（目录层级、引用块与争议框样式要对齐，别出现两套 looks）。
- ❸ CF Email Obfuscation 会把 `hello@` 改成 `[email protected]`，体检正则会误报，**人工排除即可**，不是真问题。

## 六、回滚

- 回滚前一步：`11-运营/scripts/backup-site.sh` 的快照（保留 6 份），用 `backup-site.sh --verify` 确认可用。
- 页面级回滚：把备份里的 HTML 重新 `POST /pages/<id>` 覆盖回去（**按 ID，不要按 slug** —— `slug=5000years` 查出来的是 id=79 不是真身 32）。
- 主题回滚：换回上一版 `05-发布包/*.zip`。

> **改动评审**：本次窗口 X 个文件变更，其中影响线上 N 项：<一句话列出来>
