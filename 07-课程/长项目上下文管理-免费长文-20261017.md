# 体验版 0 元，22 天烧掉 4,014 积分：我把记忆文件从 15,682 字压到 3,398 字

> 一个个人创作者 · 2026-10-17
> 本文所有数字都来自我自己项目的实测记录，出处附在文末。**能查到的我不凭印象写，估算的我会标明是估算。**
> 如果你也在用一个 AI 工具长期做一件事——不是问一句答一句，而是连续几周推进同一个项目——下面这些坑你迟早会踩到。

---

## 一、症状：任务越做越贵，而且贵得没有道理

先描述一下那个感觉。

同样一件事：让它帮我改一段网页代码、整理一份清单、检查几个文件的格式。**第一天做是 3 分，第二周做同样的活，30 分起步。**

我是一个人在做一个中文汉字演变的壁纸站（域名就不放了，不是重点）。到今天第 22 天。我这 22 天的账本如下：

| 项 | 值 |
|---|---|
| 套餐 | **体验版**（不是付费会员，我确认过账户状态字段是 `false`） |
| 22 天累计消耗 | **4,014.47 分** |
| 近 7 天请求次数 | **139 次** |
| 近 7 天消耗 | 1,695.41 分，日均 242.2 |
| 单日峰值 | **633.52 分**（某天重做了一批配图） |

这不是“用了很多高级功能”。我没有用来写长篇小说，也没有跑大模型训练。**我在做的事情，是和一个助手持续讨论同一个项目：它得记住我们之前定的规矩、之前做过的决定、之前犯错修好的地方。**

问题就出在“记住”这两个字上。

---

## 二、第一反应通常是错的：不是文件太多

大部分人（包括当时的我）遇到“变贵了”，第一反应是：**东西太多了，清理一下就好了。**

我去翻了本地目录，发现光是工具自己的运行痕迹就攒了 **106MB**，再加上一堆文件快照 **30MB**。一百多兆，看着就让人心慌。于是我把它们清了。

**结果：一分钱没省。**

为什么？因为**这些文件根本没进过上下文**。它们躺在磁盘上，占的是硬盘，不是每次请求的额度。删掉它们，和你的账单毫无关系。

这是我交的第一个学费：**磁盘和上下文是两回事，清磁盘救不了积分。**

---

## 三、四个我以为对、其实是错的事

### 1. 自动压缩不是线性的，它是锯齿

我以为：历史会越攒越多，成本一路涨到天上去。

实际不是。工具自己会压缩——攒到一个阈值，“啪”地一下把整段历史换成一段摘要。**我实测过一次：压缩点前的上下文是 30MB，压缩后就剩 6.3K 的摘要。**

这意味着两件事：

- **有天花板**：它不会无限涨，所以“再这样下去会用不起”的恐慌是多余的；
- **有回落**：但反过来，你也别指望“等等就好”——回落到摘要之后，**那些细节就真没了**，下次你得重新讲一遍，那才是真的贵。

**它是一条锯齿状的线，不是一条上升的直线。**理解这一点，比清理任何文件都重要。

### 2. 你以为它在“回忆”，其实每次都是重发

这是最反直觉的一条。

你心里以为的对话：它记得我们上次聊了什么，所以接着聊。

实际发生的：你每发一条新消息，系统都把**前面所有的相关历史重新发送一遍**。它不是在回忆，是在**重读**。

所以真正决定成本的，不是你这次问了什么，而是**这个会话有多老了**。

由此得出一条我这 22 天最贵的一条经验：

> **「回想上次会话我们说过什么」 ——这句话本身就是成本失控的来源。**

只要我发现自己正在试图从对话里“回忆”某个结论，那就说明：**这个结论早该被写到一个文件里，而不是留在会话里。**

现在我的规矩是：一个主题做完就开新会话，结论落在文档里。**会话历史不是信息源，文档才是。**

### 3. 写多少字几乎不花钱，配不配图才决定

这条是我最意外的一条。

我原以为“让它写长东西”最贵。实测下来恰好相反：

- 让它生成一张图：**5–10 分**
- 让它生成一段 5 秒视频：**50–100 分**
- 让它写几千字、做表格、跑本地脚本：**约等于 0 分**

我把自己的账目按“配图”和“文字”分了一下：**配图占了 79%，文字只占 21%。**

结论很直接：**你写一万个字几乎不影响账单，你多配十张图就影响很大。**

如果你觉得 GPT 类工具太贵，先别急着减少使用——**先看看你是不是顺手让它配了太多图。**

### 4. 开新会话能省的钱，没有你以为的那么多

既然每条消息都要重发历史，那是不是“勤换会话”就行了？

我实测过一次单次请求的构成：

| 构成 | 大小 | 能不能省 |
|---|---|---|
| 固定系统提示 | 约 20K tok（**估算值**） | ❌ **省不掉** |
| 记忆文件注入 | 6.3K | ✅ 能省 |
| 压缩摘要 | 3.9K | 部分能省 |
| 本轮对话 + 工具调用 | 9.3K | 部分能省 |

**能动的只有那 19.6K 的“可变部分”。**而其中真正长期存在的、每天都要被重复注入的，是那个 **6.3K 的记忆文件**。

所以真正的杠杆不是“开新会话”，而是——

---

## 四、真杠杆：成本 = 轮次 × 当前高度

这是我最后得出的公式，也是全文唯一需要你记住的一句：

> **一次请求的成本 ≈ 轮次数量 × 每一轮时上下文的高度**

两个变量。轮次好理解，你问一百句就比问十句贵。**真正阴险的是后半句：上下文的“高度”。**

它在会话开始的时候很低，然后随着对话越堆越高，直到触发压缩又掉下来（锯齿）。**你在高度已经很高的时候问的问题，比在低的时候问同样的问题贵得多。**

所以省钱的优先级是：

```
① 降低每一轮的“当前高度”  ← 这才是大头，也就是把记忆文件压薄
② 减少不必要的轮次        ← 一个清楚的请求，好过五轮来回拉扯
③ 少让它配图              ← 文字几乎不花钱
① >> ② > ③
```

## 五、方法：把记忆文件改成“索引模式”

现在说具体怎么做。我的记忆文件经历了三个阶段：

```
初版      15,682 字符   ← 什么都往里写，写成了一本说明书
压缩后     8,859 字符   ← 删掉了重复和过期内容
索引化后   3,398 字符   ← 只留路由 + 红线摘要，主题全部下沉
```

**降幅 78%。**

关键在于，第三版不是“把第二版写得更短”，而是**结构变了**。我把它从一个“文档”改成了一个“目录”：

### 三个原则

**① 宪法常驻**

每次都用得上的东西，留在最上层。我把它叫“宪法”——比如“风险优先于进度”、“失败一次就降级不要反复重试”、“涉及改动线上内容必须先出申请单”。

这些东西**必须每次都在**，因为它们管的是行为，不是信息。

**② 主题下沉**

按主题拆到独立文件里。拆分的原则很简单：

> **会被一起读的内容，放在一起。不会被一起读的，拆开。**

比如“如何发布到服务器”和“商品的定价规则”，这两件事永远不会在同一次对话里被同时用到——那就拆成两个文件。

**③ 命中才读**

这是最省的一步。上层文件里对每个主题只留**一行**：

- 指向哪个文件
- **一句浓缩过的红线摘要**（这行摘要要写得读完就够用）

这样大多数时候，**读完那一行就知道要不要打开文件了**。**没有命中，就永远不打开它。**

我在自己的实践里发现一个规律：**那些“为了以防万一先留着”的内容，90% 永远不会被读到，却 100% 参与了每一次注入。**

### 两个容易忽略的细节

- **日志不要塞进记忆**。它每天都在长，但你需要回溯的概率极低——压缩它毫无收益，因为它本来就不该在那儿。
- **有些标题不能改**。如果你也做了自动化脚本去读你的记忆文件，注意：**正在被程序按标题解析的段落，一律别动格式**。我踩过一次，脚本读不到东西，白忙半天。

## 六、今晚就能做的三件事

不需要任何工具，你今晚就能做：

**1. 先量一下你的记忆文件有多大。**
找到它，看字符数。**如果你答不上来这个数，这篇文章你白读了。**

**2. 找出三条“每次都用”的规矩，单独放在最上面；其余的全部挪走。**
判断标准很粗暴：**过去一周有没有用到它？**没有就挪走。

**3. 给每个挪走的主题写一句话摘要。**
要求：**读完这句话，就能判断这次要不要打开它。**

做完这三步，大概率你的文件会掉一半以上。**它不会让你的工作变少，但会让每一轮对话都便宜一点——而你的项目不是一天做完的。**

---

## 七、一个提醒：这不是“省钱技巧”，是“长期做事的方法”

最后说点务虚的。

我一开始研究这些，是因为心疼积分。**但做完了发现，最大的收获不是省了多少钱，而是被迫把自己的项目整理清楚了。**

因为你要回答一个问题：**哪些东西，是我在任何一次对话里都不愿意重讲的？**

这个问题的答案，才是你真正的资产。剩下的都可以下沉、可以压缩、可以丢。
