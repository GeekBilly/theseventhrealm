# 第 04 章 · 让 AI 安全接管网站：WordPress 权限接入实录

> 本章回答一个所有非技术站长都会焦虑的问题：**把网站交给 AI，会不会被它搞坏？**
> 答案是：能，但要做到「权限只给内容层、改动必须过审批、出事一键回滚」。本章是完整实操记录。

---

## 一、为什么不能直接把管理员密码给 AI

| 做法 | 风险 |
|---|---|
| 给管理员主密码 | AI 能改主题、装插件、删用户、改站点地址——一次误操作就可能让网站打不开 |
| 给管理员的 FTP/主机面板 | 同上，且无法按操作粒度审计 |
| **给一个「编辑」角色的应用密码** | ✅ 只能改内容，碰不到架构层；可单独撤销，不影响自己账号 |

**核心原则：给 AI 的权限，应该刚好够它干活，多一分都不给。**

## 二、方案：WordPress 原生「应用密码」

WordPress 5.6 起内置 Application Passwords，无需装任何插件：

1. 建一个**专用账号**（本案例用户名 `MollyBot_No.2`），角色选 **编辑（Editor）**
2. 用该账号进「个人资料」→ 底部「应用密码」→ 命名 `WorkBuddy` → 生成
3. 得到一串形如 `O8P7 emhZ DBXA dUtj TbKA 8i7P` 的密码，配合用户名走 HTTPS Basic Auth 调用 REST API
4. 随时可在同一页面「撤销」，一键失效

> ⚠️ 应用密码只走 https，明文 http 下不可用——所以**必须先有有效 SSL**（见第 03 章的连锁关系）。

## 三、接入前必做的三项只读探测

不要急着写内容。先确认这三个问题，否则后面全是坑：

```bash
S=https://example.com

# ① 接口是否开放
curl -s -o /dev/null -w "%{http_code}\n" $S/wp-json/

# ② 内容是否可读（未登录）
curl -s -o /dev/null -w "%{http_code}\n" "$S/wp-json/wp/v2/pages?per_page=5"

# ③ 写入通道是否被 WAF 拦截（关键！）
curl -sS -X POST "$S/wp-json/wp/v2/pages" -H "Content-Type: application/json" \
  -d '{"title":"probe"}'
```

**本次实测结果**：① 200 ② 200 ③ 返回 **401 + `"您不能为此用户创建文章。"`**
——这条 401 是**好消息**：说明请求成功抵达 WordPress 并被正确鉴权拒绝，没有被 Cloudflare 的 WAF 拦在半路。如果返回 403 且带 Cloudflare 的 HTML 拦截页，就要去 Cloudflare 安全规则放行 `/wp-json/` 路径。

## 四、必须验证权限边界（本章最重要的一节）

**只拿到账号不算接入成功，必须证明「它做不到越权的事」。** 用五个探针逐项验证：

```bash
A=(-u '用户名:应用密码')

curl -sS -o /dev/null "$S/wp-json/wp/v2/settings"           -w "settings: %{http_code}\n"
curl -sS -o /dev/null "$S/wp-json/wp/v2/plugins"            -w "plugins: %{http_code}\n"
curl -sS -o /dev/null "$S/wp-json/wp/v2/themes"             -w "themes: %{http_code}\n"
curl -sS -o /dev/null "$S/wp-json/wp/v2/users/1?context=edit" -w "users/edit: %{http_code}\n"
curl -sS -o /dev/null "$S/wp-json/wp-site-health/v1/tests/background-updates" -w "site-health: %{http_code}\n"
```

**本次实测结果（全部符合「编辑角色」预期）**：

| 探针 | 期望 | 实测 | 结论 |
|---|---|---|---|
| `GET /settings` | 403 | **403** | ✅ 改不了站点设置 |
| `GET /plugins` | 403 | **403** | ✅ 装不了插件 |
| `GET /themes` | 403 | **403** | ✅ 换不了主题 |
| `GET /users/1?context=edit` | 403 | **403** | ✅ 读不了他人资料（无 list_users） |
| `GET /site-health/v1/...` | 403 | **403** | ✅ 拿不到系统信息 |
| `GET /pages/13?context=edit` | 200 | **200** | ✅ 有内容编辑权（编辑角色特有的 edit_pages） |
| `GET /comments` | 200 | **200** | ✅ 有内容管理权 |

### ⚠️ 一个必须避开的误判陷阱

初次探测时，`GET /wp-json/wp/v2/users` 返回了 **200**，看起来像是越权拿到了用户列表。但对照未登录请求后发现：**该接口对匿名访客同样返回 200**，内容只有「有已发布文章的作者」这一位（`id:1, name:theseventhmind`）。

> **教训：判断权限时，一定要拿「未登录请求」做对照组。** 接口公开可读 ≠ 账号越权。真正有效的判据是 `?context=edit` 这类需要能力的读法，而不是接口本身能不能访问。

### 另一个陷阱：dry-run 反而会真写

在设计自动化探测脚本时，最初写了一条「POST 一个 draft 页面来验证有没有写权限」的探针。这**极其危险**——应用密码走 Basic Auth 时无需 nonce，POST 会**真的创建页面**。

> **正确做法**：验证「有没有写权限」改用**读编辑态**——`GET /wp-json/wp/v2/pages/{id}?context=edit` 返回 200 就证明具备该资源的编辑能力，全程零写入。

## 五、配套的治理约定（比技术更重要）

1. **权限只到内容层**：编辑角色改不了主题，所以「子主题安装」这类架构操作仍由站长手动上传 zip
2. **首次写入另发申请单**：接入本身只做只读验证；AI 想改任何一个字，都要先发「改什么/影响范围/怎么回滚」的申请给站长批准
3. **凭据不入库**：应用密码不写进任何记忆文件或文档，只在使用会话中传递；若日后要做「定时任务自动发布」，必须单独批准后存进受限文件（`chmod 600`）
4. **定期轮换**：完成一段密集工作后撤销旧密码、重新生成

## 六、什么时候该收回权限

- 密集改动期结束 → 撤销密码，仅留人工通道
- 需要 AI 做「架构层」操作（换主题、装插件）→ 临时开更高权限，**做完立刻收回**
- 站点交接、多人协作 → 每人独立账号独立密码，便于审计

## 附：把凭据摩擦降到零（2026-09-29）

### 一、先问「这个麻烦真的必要吗」

最初的做法是：每次要写站，让用户到 WordPress 后台生成一个应用密码，用完立刻撤销。听起来很安全，其实是**安全表演**：

- 应用密码**本身不会过期**，WP 里可以给每个密码设单独名字、单独撤销；
- 但"每次生成一次、事后撤销"的真实代价是：用户每次都要登录后台 → 找到个人资料 → 生成 → 抄写 24 位密码 → 贴给 AI，用完还得回来撤销；
- 一天来回几轮，摩擦成本远大于它挡住的风险 —— 而那个风险（密码泄露）**用"事后撤销"也没真正解决**（用完之前它是有效的）。

**关键判断**：这个麻烦是"重复出现"的，且不涉及不可逆的对外动作 → 就该自动化。

### 二、凭据放哪：三档安全性

| 方案 | 安全性 | 自动化 | 结论 |
|---|---|---|---|
| 写在项目文件 / 脚本里 | ❌ 会随 git、备份、误发外泄 | ✅ | 绝对不做 |
| 明文存 `~/.secrets`（chmod 600） | ⚠️ 同等权限的进程都能读 | ✅ | 可接受的退路 |
| **系统钥匙串**（macOS Keychain） | ✅ 由登录密码加密、系统级保护、可按 App 授权 | ✅ | **首选** |

macOS 上一条命令即可：

```bash
security add-generic-password -a "bot-account" -s "my-site" -U -w "<应用密码>"
security find-generic-password -s "my-site" -w      # 脚本里读
```

配一个 `wp-auth.sh`：**优先读环境变量，其次读钥匙串**。这样既保留"临时给一次"的能力（`WP_APP_PASS='…' bash xxx.sh`，用完即丢），又让日常操作完全无感。

### 三、权限最小化仍是底线

自动化不等于放权。这个账号是**编辑角色**，实测改不了设置/插件/主题/用户（全 403），只能编辑页面、上传媒体。真正的护栏是**角色权限**，不是"每次换密码"。

配套的两条规矩：
1. **能力最小化**：能发页面就不给管理员。
2. **动作分级**：日常读改（草稿、预览、体检）直接做；**上线、删改线上内容、主题变更、涉及钱**必须先发执行申请单等批准 —— 护栏放在"动作"上，而不是放在"凭据"上。

**一句话**：安全应该靠**权限分层 + 动作审批**，而不是靠**让用户反复搬运密码**。
