## 〇、一句话结论

> **不要让三端"同时编辑同一个项目"——这是多人协作的模型，会拖垮一个人。**
> 正确模型是：**一个真源 + 一台主机 + 两个瘦客户端**。
> 而"不用重复解释"的钥匙不是买更好的同步工具，是**把"现在在干什么"从流水账里拎出来，单独放一个文件**。

## 一、先诊断：你的三个"断档"分别是哪三个

### 1.1 上下文断档（最贵，今天就能治）

**症状**：换个机器/开个新会话，就得把背景再讲一遍。

**根因**：说过的东西没落在**可寻址的位置**——它要么在上一轮对话里死了，要么淹没在日志里。

实测你的记忆层现状：

| 文件 | 现状 | 问题 |
|---|---|---|
| `.workbuddy/memory/2026-09-30.md` | **171 KB** | 单日日志已超过一次能读的上限 |
| `.workbuddy/memory/2026-10-01.md` | 90 KB | 同上 |
| `.workbuddy/memory/MEMORY.md` | 6.8 KB，**硬上限 8000 字符** | 被迫反复"下沉压缩"，规则细节在压缩中丢失 |

**缺的是第三种文件**：日志记"过去发生了什么"（append-only，越滚越大），MEMORY 记"永远成立的事"（被字数卡死），
但**没人记"此刻在干什么、下一步是什么、卡在哪"** —— 而这恰恰是你每次换端最需要的一句话。

→ **创建 `NOW.md`（覆盖写）**。这是本次最高优先级动作，成本 5 分钟，收益覆盖所有端。

### 1.2 资源断档（次之，需要动土）

实测：

| 项 | 实测值 | 影响 |
|---|---|---|
| 工作区大小 | **1.8 GB** | 02-商品 940M / 11-运营 565M / 08-音频 163M |
| 文件总数 | ≈ 4,500（含 1,575 张 PNG） | |
| **硬编码绝对路径的文件** | **674 个**（436 html / 113 py / 36 sh / 13 md） | ⚠️ MEMORY 里记的"131 个"已过时，别再引用 |
| Git | **不是仓库** | 没有任何版本历史，改坏了不可回滚 |
| 工作区位置 | 本机 `~/WorkBuddy/2026-09-25-15-56-17` | 不跨设备 |
| LaunchAgent | `deepseek-balance` / `cf-security` 两条**绑在本机** | 换机器即静默失效 |

**674 的意义**：不能靠"改 674 个文件"来搬家，必须靠**让新位置看起来像旧位置**（见 §3.2 的 symlink 技巧）。

### 1.3 能力断档（被忽视的一条）

你已经积累的东西，比工作区里任何一份文件都难重建：

| 资产 | 现在在哪 | 跨端？ |
|---|---|---|
| `ink-wash-web-design` skill | `~/.workbuddy/skills/`（2.0 MB） | ❌ 本机独占 |
| `qijing-wallpaper-paradigm` skill | 同上 | ❌ 本机独占 |
| 4 条云端定时任务 | 云端 | ✅ 天然跨端（但 `cwds` 指向本机路径） |
| 72 个 `11-运营/scripts/*.py` | 项目内 | 随项目走 |
| WordPress 应用密码 | **钥匙串**（`theseventhrealm-wp`） | ❌ 需逐机重建 |
| Bash 陷阱 / Chrome 沙箱坑 | 已整理进 `11-运营/自动化与取数手册.md` | ✅ 已文档化（这是正确的做法） |

**判断原则**：**凡是"配置信息"（存在 `~/` 下、不在项目目录里的），都 100% 不跨端。**
→ 必须逐个识别、逐个安排搬家路线，见 §3.5。

## 二、核心架构：三层，不是一个工具

```
┌─ 第 1 层：单一真源 ──── 所有的"状态"只有一个物理版本 ────┐
│  iCloud Drive（或 Git）承载工作区，三端读的是同一份       │
└──────────────────────────────────────────────────────┘
┌─ 第 2 层：上下文加载 ── 解决"不用重新解释" ─────────────┐
│  NOW.md（当前） + MEMORY.md（永久） + 日志（过去）        │
│  → boot 协议固化成 skill，三端共用同一份                  │
└──────────────────────────────────────────────────────┘
┌─ 第 3 层：设备分工 ──── 决定"哪台机器干哪件事" ──────────┐
│  Mac mini＝引擎房 / MacBook＝驾驶舱 / iPhone＝遥控器      │
└──────────────────────────────────────────────────────┘
```

### 2.1 三端角色表（这是架构的灵魂）

| 端 | 角色 | 干什么 | **严禁干什么** |
|---|---|---|---|
| **Mac mini**（插电常驻） | **引擎房** | 跑定时任务、渲染出图、备份、自动 commit、Chrome 批处理 | ❌ 不写稿 ❌ 不做决策 ❌ 不开会话纠结 |
| **MacBook**（随身） | **驾驶舱** | 写作、决策、审批、主持 AI 会话 | ❌ 不跑长任务（合盖即断） |
| **iPhone** | **遥控器 + 捕手** | 读日报、批/驳待办、录语音灵感、拍素材、看预览链接 | ❌ **不编辑核心文件**（见下） |

**关于 iPhone 的关键纪律**：不要试图在手机上改 md 正文。
正确做法是 iPhone 只往 **`12-Inbox/`**（收件匣）里丢零碎，正式改动由 Mac 上的会话读取 inbox 后统一执行。
理由：手机上改文件没有 `path-links-check.py` / `lint-cjk-text.py` 体检，也没有回滚——**省一步的代价是污染真源**。

**为什么这么分**：你的时间预算是**每周 310–470 分钟**，其中深度生产仅 ≈13.7 小时/月。
这个约束下，任何需要"额外操作纪律"的制度都会死。所以：
- 让**重活集中在永不关机的机器**（不需要你在场）
- 让**决策集中在一台机器**（不需要同步 Multiple state）
- 让 iPhone **只投喂不改**（不制造需要清理的现场）

## 三、执行清单

> 按"S（体验）→ A（可重建但贵）→ B（随时可重建）"给文件分级，是本方案的省力核心。

### 文件分级表

| 级 | 内容 | 量级 | 同步？ | 入 Git？ |
|---|---|---|---|---|
| **S 源** | `*.md` `*.py` `*.sh` `*.csv` `*.json`、版式模板 HTML、`seventhrealm-child/`、`.workbuddy/memory/` | ≈50 MB | ✅ 实时 | ✅ 必须 |
| **A 产物** | 壁纸成品 PNG（`03-字形线/成品/`、`06-姓氏线/成品-*/`）、音频成品 | ≈940 MB | ✅ 实时 | ❌（体积 + 不可 diff） |
| **B 派生** | 样张/校样/预览图、`11-运营/backup/`、`05-发布包/*.zip`、`browser-profiles/` | ≈800 MB | ❌ **不同步** | ❌ |

> A 级为什么必须同步：那些 PNG 是烧过 ImageGen 积分的成品，**丢了大概率无法低成本复原**。
> B 级为什么不同步：跑一遍脚本就能重新生成，同步它们只是给 iCloud 交学费。

### P1 · 两周内做（⚠️ 需先出执行申请单，要你拍板）

> 🔄 **已降级为备选**：选定 §七 的原生多端方案后，文件级同步已无必要，本节一般不执行。
> 保留价值：① 容灾（Mac mini 不可用时要在别的机器上有完整可运行环境）；② 未来想让多台机器**同时本地体格干活**时才需要。
> **若采用 §七，直接跳到 P2。**

选一条路线，**不要两条同时上**：

#### 🅰 A 案：iCloud + 符号链接（推荐）

```
① 在 iCloud Drive 里建【无空格、无中文】的目录：
   ~/Library/Mobile Documents/com~apple~CloudDocs/workspace-7th/
② 把 ~/WorkBuddy/2026-09-25-15-56-17/ 的内容整体搬进去（先搬 S+A，B 级留本地）
③ 在原位建符号链接，指向 iCloud 真身：
   ln -s ".../workspace-7th" ~/WorkBuddy/2026-09-25-15-56-17
④ 三台 Mac 各自重复 ③（真身只有 iCloud 里的一份）
```

**为什么这样能"零改动"**：674 个文件里写死的字符串是 `/Users/billyhou/WorkBuddy/2026-09-25-15-56-17`。
符号链接让这个路径在三台机器上**都存在且指向同一份真身** —— **一个字都不用改，包括 4 条定时任务的 `cwds`。**

**四条必须遵守的约束**：
1. iCloud 目录名**必须无空格无中文**（iCloud 真实路径含空格，若脚本调 `os.path.realpath` 会炸）
2. **符号链接只建在本机**，别把符号链接本身放进 iCloud（会同步成一个死文件）
3. 三台 Mac 一律**关闭「优化存储空间」**（否则文件被踢到云端变占位符 `.icloud`，Python 脚本读到会炸）
4. 大搬家当天，**只让一台 Mac 在线完成上传**，第二台再开机

**已知风险**：初次上传 ≈1 GB，视带宽数小时；上传完成前不要在另一台机器开工。

#### 🅱 B 案：Git 主同步（不推荐作为唯一方案）

优点是有真历史、可回滚。缺点致命：**需要人工 `commit` / `pull` 纪律**。
你每周只有 6.5 小时且主业是金融，Git 分叉是时间问题，而分叉后的合并成本远超收益。

#### 🅲 C 案（最佳实践，但放第二阶段）

**A 案负责"实时"，Git 负责"历史"**：在 A 案跑顺后，加一条 LaunchAgent **每天自动 `git add -A && git commit`**（无人值守）。
Git 只跟踪 S 级文件（`.gitignore` 排除 A/B 级），仓库体积控制在 50 MB 内。

> **你不需要记得 commit，机器替你 commit。** ——这是一人公司唯一能活下来的 Git 用法。

## 四、一人公司的经营架构（你缺的那部分知识）

### 4.1 四个角色模型 —— 你的 AI 会话就是你的团队

一人公司不是"一个人干所有事"，是**一个人轮值四个岗位**。你现在 unbalanced 得很明显：

| 角色 | 职责 | 第七境现状 | 判定 |
|---|---|---|---|
| **产品官** | 做什么、不做什么、什么顺序 | 内容严重超前（8.2 万字已写完），商业为零 | ⚠️ 偏弱：做得多、判得少 |
| **生产者** | 执行产出 | 119 事件节点 + 40 张成品 + 14 章大纲 | ✅ **过强** —— 产能已过剩 |
| **运营官** | 分发、度量、转化 | **0 邮箱 / 0 上架 / 0 元** | 🔴 **最弱，且是唯一瓶颈** |
| **风险官** | 合规、备份、续费、商标 | R-19 冻结 + 备份演练 ✅ + 商标九轮收官 | ✅ 意外地强 |

**结论**：**你不缺能力，你缺的是把"生产者"的时间转移给"运营官"。**
第 1 年的每一分钟都应该问一句：**这件事能带来邮箱吗？能带来第一笔钱吗？** —— 答不上来就往后排。

### 4.2 五条定律（一人公司专用）

1. **约束定律**：每周只有 6.5 小时 → **任何需要"额外操作纪律"的制度必定死亡**。能自动化的自动化，不能自动化的砍掉。
2. **瓶颈定律**：同时做十件事等于一件事也没推进。当前唯一瓶颈是**邮箱数**；排在它前面的所有任务，无论多紧急都是伪紧急。
3. **沉淀定律**：**同一件事做到第三次之前必须脚本化 / skill 化**。第三次还在手做 = 你在给未来的自己挖坑。
4. **决策日志定律**：一人没有同事纠偏，最容易的不是做错，是**反复摇摆**。把决策及其触发条件写死在文件里，下次只对齐条件，不重开讨论。
5. **止损定律**：一人公司最常见的死法不是失败，是**无限期投入**。必须有预先写好的降级条件（你已有"连续 2 个月 🔴 触发降档" —— 这是对的，要继续加收入侧的条件）。

### 4.3 你该盯的四类数字（不是越多越好）

| 类 | 指标 | 频率 | 为什么 |
|---|---|---|---|
| **现金流** | 收入 vs 主机 vs AI 积分 | 月 | 唯一的生存指标 |
| **瓶颈** | 邮箱数 / 上架 SKU 数 | 周 | Y1 唯一瓶颈 |
| **产出** | 发布页数 / 引流文篇数 | 周 | 领先指标，预示 2–4 周后的流量 |
| **风险** | 域名到期 / 证书剩余 / 商标新增 / 积分跑道 | 月 | ⚠️ 积分按 `fetch-credits.sh` 真实值，**不许凭记忆报数** |

### 4.4 长期建设清单（按年）

| 时间 | 建设项 | 验收标准 |
|---|---|---|
| **Y1（现在）** | 三端单一真源跑通 + 决策日志习惯 + 邮箱破 0 | 在任意一台机器开会话，5 分钟内能接续昨天的活 |
| **Y1 底** | ombres第一条现金流 + 扣税/结汇路径验证 | 出现第一笔真实收入并完成合规申报 |
| **Y2** | 外包第一件按件工作（插画/剪辑） | 完成一次完整发包与验收，你只负责判断不负责执行 |
| **Y3** | 版权登记完成 + 首个授权/分销谈判 | 出现不需要你额外投入时间的收入 |
| **Y5** | 微型 IP 工作室：固定的 1–2 名外部协作者 | 你休假两周，项目不中断 |

## 五、两个立即可用的模板

### 5.1 `NOW.md` 模板（每次收工**覆盖写**，别 append）


## 七、主方案：单机执行 + 三端遥控（2026-10-08 修订）

> 这一节取代了初版的核心思路。**关键改变：不再同步文件，而是让三台设备操控同一台机器。**

### 7.1 WorkBuddy 原生多端协同（免费，已具备）

官方文档（`/docs/workbuddyapp/features/Multidevice`）确认的能力：

| 能力 | 说明 |
|---|---|
| **远程续聊** | 手机进入**同一个对话**继续发指令，**指令在桌面端执行** ⇒ 上下文天然共享，不是重新起会话 |
| **遥控执行 / 停止** | 手机可授权、可一键终止偏离预期的任务 |
| **任务/对话/产物同步** | PC · App · 小程序三端实时同步 |
| **主动推送** | 任务完成、等待回答、等待审批 → **推送到手机，点击直达** |
| **远程配置** | 技能/专家/连接器/权限/模型手机上也能配，**以电脑端为准** |
| **双层状态** | 设备级 + 对话级状态标识，绿点＝在线且在跑 |

**版本**：PC ≥ 5.3.8、App ≥ 1.2.0。**本机已是 5.7.6 ✅**

### 7.2 开启步骤（一次性）

在 **Mac mini（定为唯一执行机）** 上：

1. WorkBuddy 侧边栏**底部**悬停「连接移动端」图标 → 打开「**允许移动端连接此设备**」
2. 打开「**保持唤醒状态，以便远程访问**」（macOS 侧：系统设置 → 通用 → 允许锁屏运行）
3. Mac mini 电源：**永不休眠** ＋ 勾选「断电后自动启动」
4. WorkBuddy 加入**开机自启**（否则重启后多端连接静默断开）
5. 手机装 WorkBuddy App，**登录同一账号** → 侧边栏顶部设备入口 → 选中这台 Mac mini

> **MacBook 怎么用**：两种都对。**推荐把它也当成控制台**（连到 Mac mini），
> 只在明确需要本地跑时才直接用本机 —— 一旦两边各自本机执行，就会重新出现文件分叉。
> **纪律：同一时刻，只在 Mac mini 上有"正在改动文件的会话"。**

### 7.3 代价：备份必须升级（必修，不是选修）

新方案把所有鸡蛋放进一个篮子，**这是它唯一的重大代价**。必须同时具备三层：

| 层 | 手段 | 频率 | 防什么 |
|---|---|---|---|
| **本地回滚** | **Time Machine**（挂一块硬盘给 Mac mini） | 每小时 | 误删、改坏、脚本跑错 |
| **版本快照** | **每日无人值守自动 commit**（Git 只跟踪 md/py/sh/csv/json） | 每晚 | "三天前那个版本说的是什么" |
| **异地生存** | 关键资产同步到 iCloud / 对象存储 | 每周 | 机器坏了、丢了 |

> 只做一层等于没做。**备份的重要性在这个方案下比原来高一档。**

### 7.4 第三方软件选型（用户问的具体清单）

> 原则：**每加一个工具都要能回答"它替我解决了哪件原本做不成的事"**。答不上来就不装。

#### ✅ 建议装（各补一个明确的短板）

| 软件 | 平台 | 费用 | 补什么短板 |
|---|---|---|---|
| **Tailscale** | Mac / iOS / Win | **免费**（个人 100 设备内） | **单点故障的保险**。组虚拟局域网后，即使 WorkBuddy 云端通道不可用，仍能从手机直接 SSH / 屏幕共享到 Mac mini 救急。配置约 5 分钟 |
| **Time Machine** | Mac | 免费（需一块硬盘） | 上面 7.3 的第 1 层，不可省 |
| **Obsidian** | Mac / iOS | 免费（Sync 付费可选） | 补的是「**找不到东西**」，不是同步。把整个项目当 vault 打开 → 全库全文搜索 + 双链，对 4,500 个文件的项目价值极高 |
| **Blink Shell** 或 Termius | iOS | 一次买断 | 配合 Tailscale，手机上敲命令救急（重启 LaunchAgent、看 log） |

> ⚠️ **Obsidian 用法注意**：只在 Mac mini 本机把 vault 指向工作区，
> **不要**再开一层 Obsidian Sync / iCloud 同步——否则等于给同一批文件加第二个同步源，反而制造冲突。

#### 🤔 可用可不用

| 软件 | 判断 |
|---|---|
| **Git + GitHub** | **不要当同步**；当"每日自动快照"则强烈建议（见 7.3 第 2 层）。关键是**无人值守**，靠你手动 commit 一定忘 |
| **Working Copy** | 只有真要"在手机上操作 Git"才需要；日常不需要 |
| **Syncthing** | Mac↔Mac 很好且开源，但 iOS 客户端残缺。新方案下没必要 |

#### ❌ 明确不建议

| 方案 | 为什么 |
|---|---|
| Dropbox / OneDrive | iCloud 已在用，再加一个云同步源只会互相打架 |
| 任何"把 1.8 GB 实时同步到三处"的方案 | 已被 §七 消解，纯属给自己找运维活 |
| **在 iPhone 上编辑核心文件** | 与初版纪律一致：手机上没有 `path-links-check.py` / `lint-cjk-text.py`，也没有回滚 |

## 八、数据层选型：要不要数据库 / Notion

> 先给结论：**现在不需要数据库；Notion 可以用，但只能当消费端，不能当源。**

### 8.1 用四条标准判断，而不是凭感觉

| 判断标准 | 第七境现状 | 结论 |
|---|---|---|
| **并发写入**（多人同时改同一条） | 一人公司 | ❌ 不需要 |
| **事务 / 一致性**（钱、订单、库存） | 收入 ¥0，`revenue.csv` 空 | ❌ 不需要 |
| **程序远程读写** | 全在本地跑脚本 | ❌ 不需要 |
| **数据量超出文件承载** | **最大一张表 183 行** | ❌ 差三个数量级 |

**实测规模（2026-10-08）**：

| 台账 | 行数 |
|---|---|
| `01-内容/典籍库/canon.csv` | **183** |
| `01-内容/历史长卷/事件库/all.csv` | **120**（119 事件节点） |
| `11-运营/data/risk-log.csv` | **51** |
| `04-市场/05-客户库/客户库.csv` | **1**（只有表头，0 订阅者） |

> CSV 的舒适区是**几万行**。你现在是**百行级**。
> 这个量级上数据库带来的不是能力，是运维负担和新的依赖。

### 8.2 那"东西太散、看不出全局"怎么办

**这是真痛点，但解药是「视图层」，不是「数据库」。**

散的是文件，缺的是汇总。你已经有的正确做法：`积分仪表盘-*.html`、`DeepSeek-余额曲线.html`。
把它制度化即可：

- **每周自动生成一个「总览仪表盘」HTML**，汇总：邮箱数 / 上架 SKU / 收入 / 积分跑道 / 域名证书剩余 / 商标待办 / 本周产出。
- 一个文件、可被脚本读、iPhone 上能打开（<500 KB）、不需要任何 SaaS。

### 8.3 Notion：诚实评价

**它真正强的三点**：手机端体验远好于读 md；看板/日历视图一眼看到"这周发什么"；随手记零摩擦。

**但对本项目的三个硬问题**：

1. 🔴 **不在文件系统里** ⇒ 72 个 Python 脚本、`path-links-check.py`、`lint-cjk-text.py` **全部读不到它**。
   放进 Notion 的数据就**脱离了自动化流水线**，只能靠人手维护。
2. 🔴 **它会成为第二个真源** —— 而这正是 §七 刚刚费力消除的东西。
   客户库/商标台账一旦两边各有一份，不一致是迟早的事。
3. 🔴 **个人信息合规**：`客户库.csv` 里存的是**真实订阅者邮箱**。把个人信息放进境外 SaaS，
   等于引入第三方处理者。你此前已经为同一类问题做过一次正确判断
   （"不把订阅信转发到 AI 邮箱自动读取——不值得为省一步引合规敞口"），此处同理。

**所以边界很清楚**：

| 放得进 Notion | 🔴 绝不放 |
|---|---|
| 内容日历、选题库、课程大纲、灵感速记 | 客户邮箱、商标证据与凭据、任何会被脚本读的源数据、任何带真实个人信息的东西 |

**并且必须单向**：Notion 只作草稿与消费端，正式数据一律回写文件。

### 8.4 更贴合的替代：Obsidian

本地 md、能进 Git、脚本能读、手机可读、有看板与 Dataview 插件。
**给你 Notion 大约八成的好处，零双源风险。**
（同 §7.4 的警告：vault 指向工作区即可，**别再叠一层 Sync**。）

### 8.5 什么时候才真的需要数据库（触发条件，任一满足即启动）

| 触发 | 那时用什么 |
|---|---|
| 出现**真实订单流水**（需要对账、需要事务） | 内置 `workbuddy_cloud_service`（对标 Supabase） |
| 需要**用户账号 / 订阅状态 / 登录** | 同上，自带认证与权限 |
| 需要 **Web 端程序读写**（小程序、站内商店） | 同上 |
| 任一单表**超过 1 万行**且需要复杂聚合 | 再评估 |

> 别自己搭 Postgres。一人公司不该有数据库运维这份工作。

### 8.6 现在真正该立的：台账三条纪律

1. **每份台账有唯一键**（客户库已做：邮箱为唯一键）——没有唯一键的台账迟早产生重复行。
2. **台账只由脚本写，不手改** —— 手改会引入格式漂移，脚本下次跑就崩。
3. **单一真源**：一份数据只有一个文件，第二份就是隐患。
